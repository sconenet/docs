# UDP + TCP DNS सर्वर (M6 + M7b) — `scone dns`

> सकोन DNS सतह का नॉर्मेटिव विनिर्देश।
> कोई भी doc/code विचलन = बग (सत्य के स्रोत को ठीक करें)।

## अवलोकन

**DNS सर्वर** रिले की एक वैकल्पिक सतह है: यह सकोन नामों के लिए
**UDP और TCP** DNS प्रश्नों (RFC 7766, वही पोर्ट) का उत्तर देता है
— **केवल चेन के विरुद्ध सत्यापित डेटा से** — और बाकी सब के लिए एक
**वैकल्पिक रिकर्सिव फ़ॉलबैक** (`addr:port`) प्रदान करता है।
यह न चेन का, न store का, न DHT का स्वामी है: अस्तित्व/समाप्ति
निर्णय **प्राधिकारी DNS स्नैपशॉट** से होते हैं (प्रत्येक लागू ब्लॉक के
बाद प्रकाशित एक RAM दृश्य — नीचे देखें), और रिकॉर्ड
प्राप्तियाँ रिले (प्रक्रिया) से, आंतरिक `RelayCommand`/`ResolveLocal`
चैनल (in-process, एक round trip) के माध्यम से — वही
सत्यापित पथ जो CLI का है।

```text
              UDP+TCP :5353 (default 127.0.0.1)
                    │
             scone relay --dns 127.0.0.1:5353
                    │  ┌────────────────────────────────┐
                    ├──┤ Sharded cache, 16 ways (qname)  │
                    │  └────────────────────────────────┘
                    │  Scone-shaped name?
                    │  ├─ YES → authoritative DNS snapshot:
                    │  │        unknown/expired → NXDOMAIN (RAM,
                    │  │        zero round trips into the core)
                    │  │        → apex search by suffix
                    │  │        → internal `resolve_local` (relay)
                    │  │           chain + verified record (hash,
                    │  │           owner, sequence) → answers
                    │  │        apex without a published record → NODATA
                    │  └─ NO → upstream fallback (if configured)
                    │           otherwise REFUSED
                    │
                    │  response budget:
                    │    UDP → 512 bytes (no EDNS); overflow =
                    │          cut at the last fitting record + TC=1 →
                    │          the client retries over TCP
                    │    TCP → 64 KiB (2-byte length prefix,
                    │          RFC 1035 §4.2.2): full set
```

## स्टार्टअप

```bash
scone relay --dns 127.0.0.1:5353            # DNS surface only
scone relay --dns 0.0.0.0:53 \
            --dns-upstream 1.1.1.1:53 \
            --dns-upstream 8.8.8.8:53       # + recursive fallback
```

रिले प्रभावी पता stdout पर घोषित करता है
(machine-readable contract, `p2p:` की तरह): socket बंधते ही
एक `dns: <addr>` पंक्ति।

सत्यापन क्लाइंट: `dig <name> --dns 127.0.0.1:5353
--qtype A` (A, AAAA, TXT, MX, NS, CNAME, ANY)।

## रिज़ॉल्यूशन पथ (AUTHORITY = चेन, सदा)

0. **प्राधिकारी DNS स्नैपशॉट**: एक अपरिवर्तनीय दृश्य
   (`Arc<HashMap<DomainId, {valid_until, has_record}>>`,
   `tokio::sync::watch` feed) जो रिले कोर द्वारा **प्रत्येक
   लागू ब्लॉक के बाद** (push, poll नहीं) और बूट पर प्रकाशित होता है।
   अस्तित्व/समाप्ति निर्णय — NXDOMAIN, समाप्त डोमेन — इस
   स्नैपशॉट से RAM से सेवित होते हैं: एक `Arc` clone + एक
   map lookup, रिले के single-owner run
   loop में **कभी प्रवेश किए बिना**। पूरा पथ
   (`RelayCommand`/`ResolveLocal`) वास्तविक
   रिकॉर्ड प्राप्तियों (DHT pulls) के लिए आरक्षित रहता है,
   जो कैश की बदौलत दुर्लभ हैं। स्नैपशॉट कभी रिकॉर्ड डेटा
   नहीं रखता: केवल अस्तित्व और समाप्ति।
   - **O(touched) copy-on-write डेल्टा**: map एक
     `Arc<HashMap>` है; tip विस्तार ब्लॉक का डेल्टा प्रकाशित करता है
     (ब्लॉक के अपने लेनदेन उन सभी डोमेनों का नाम लेते हैं जिन्हें वे बदल
     सकते हैं — Register/Assign/Update/Renew/TransferDomain — साथ ही
     push-समय पर मूल्यांकित नियतिवादी expiry-GC हटान)
     `Arc::make_mut` से: map केवल तभी clone होता है जब कोई
     पाठक पिछला दृश्य थामे हो। बूट और reorg पूरा
     स्नैपशॉट पुनर्निर्मित करते हैं (एक paged backend walk)।
   - ताज़गी: एक पाठक ब्लॉक अनुप्रयोग के दौरान कुछ सौ ms पुराना
     स्नैपशॉट देख सकता है — वही पुरानापन जो status RPC
     का होता; DNS कैश TTL अप्रभावित (उत्तर अपने
     मूल के अनुसार प्राधिकारी बने रहते हैं)।
1. **शार्डेड कैश**: [`ShardedCache`] — 16 स्वतंत्र `Cache`
   शार्ड, `hash(qname)` कुंजी से (qtype वही शार्ड साझा करता है:
   प्रति-नाम locality)। कोई हॉट नाम ट्रैफ़िक के 1/16 से
   लड़ता है बजाय हज़ारों qps पर एक mutex के पीछे कतार के। GLOBAL
   सीमाएँ (डिफ़ॉल्ट 100,000 प्रविष्टियाँ / 64 MiB,
   `--dns-cache-limit` / `--dns-cache-max-mem`) प्रति शार्ड विभाजित
   (प्रलेखित बदतम स्थिति: 1 + N/shards गुणक)। प्रत्येक प्रविष्टि का
   वास्तविक rdata आकार गिना जाता है (~128 बाइट प्रति
   प्रविष्टि overhead) और FIFO निष्कासन दोनों में से पहली
   पूरी हुई सीमा पर — पूर्ण-आकार प्रविष्टियों के
   विरुद्ध भी मेमोरी सीमा टिकती है (`MAX_DHT_RECORD_LEN`)। TTL 60 s
   (प्राधिकारी) / 600 s पर clamp (फ़ॉलबैक)। निगेटिव
   कैश (NXDOMAIN/NODATA) वही नियम; प्रत्येक प्रविष्टि
   अपना मूल (प्राधिकारी या फ़ॉलबैक) रखती है ताकि hit पर AA bit
   ईमानदार रहे। **SERVFAIL कभी कैश नहीं** (क्षणिक
   स्थानीय विफलता) **न REFUSED** (विन्यास स्थिति): दोनों प्रत्येक
   प्रश्न पर पुनर्गणित। क्षमता पर FIFO निष्कासन।
   **हॉट पथ (Cloudflare/1.1.1.1-प्रेरित)**:
   - साझा `Arc<CacheEntry>` प्रविष्टियाँ: hit एक refcount bump है,
     rdata का कभी गहरा clone नहीं (`put` Arc को बदलता है —
     कोई साझा परिवर्तन नहीं; TTL फिर भी शार्ड
     लॉक के अंतर्गत जाँचा जाता है);
   - **बिना-आवंटन लुकअप**: दो-स्तरीय map
     (`Box<str>` qname → qtype → entry), प्रश्न का उधारा
     `&str` सीधे जाँचता है (`Borrow<str>`) — पुरानी
     `(String, u16)` tuple कुंजी प्रत्येक
     लुकअप पर नई `String` आवंटित करती थी;
   - **पैक संलग्न रिकॉर्ड**: प्रति प्रविष्टि एक `Box<[u8]>` बफ़र
     (प्रति रिकॉर्ड `u16 rdlen ‖ u16 rtype ‖ u32 ttl ‖ rdata`)
     बजाय प्रति रिकॉर्ड एक `Vec` के — मेमोरी बजट
     ठीक वही गिनता है जो आवंटित है;
   - **आउटपुट पर RFC 1035 नाम संपीड़न**: प्राधिकारी
     उत्तरों का owner प्रतिध्वनित प्रश्न में एक 2-बाइट संपीड़न
     संकेतक (`0xC00C`) है — प्रश्न प्रति रिकॉर्ड पूरा पुनः-एनकोड
     कभी नहीं होता।
2. **सकोन-आकार?** सख्त पूर्व-फ़िल्टर: लेबल `[a-z0-9-_]`
   (1..63), ≥ 2 लेबल, TLD 1..63 बाइट `[a-z0-9-]` (देखें
   `TldName::MAX_LEN`), कुल लंबाई ≤ 253 — **और TLD ICANN रूट के
   बाहर** (`is_icann_tld`, जमी हुई IANA सूची + RFC 2606:
   `com`, `fr`, `org`… कभी सकोन के नहीं होंगे)।
   जो नाम सकोन नाम **नहीं हो सकता** (जैसे `www.foo_bar`,
   TLD में अंडरस्कोर) फ़ॉलबैक जाता है; संभावित सकोन नाम
   (`absent.uip`) चेन का मामला है: अपंजीकृत → प्राधिकारी
   NXDOMAIN, बिना upstream के भी। ICANN TLD (`example.com`)
   सेट हो तो upstreams को अग्रेषित, अन्यथा REFUSED —
   सकोन द्वारा कभी प्राधिकारी रूप से हल नहीं।
3. **Apex खोज**: प्रत्यय सबसे लंबे से सबसे छोटे तक (न्यून.
   2 लेबल)। पहला प्रत्यय जिसकी ऑन-चेन अवस्था रिले को ज्ञात = apex;
   रिकॉर्ड समुच्चय पूरे qname की सेवा करता है
   (सबनाम सहित — अंतर्निहित wildcard व्यवहार, खुला
   निर्णय)।
4. **`resolve_local` (आंतरिक चैनल)**: एकल round trip, कभी
   DHT waiter नहीं। ऑन-चेन अवस्था (`registered`, owner, sequence) +
   स्थानीय DHT कैश रिकॉर्ड **पुनः सत्यापित** (owner, sequence,
   record_hash == ऑन-चेन प्रतिबद्धता)। अनुरूप न होने वाला रिकॉर्ड
   कभी उत्तर नहीं देता — उपलब्धता ≠ प्राधिकार।
   - अपंजीकृत → NXDOMAIN;
   - बिना वैध रिकॉर्ड पंजीकृत → NODATA (NOERROR, 0
     उत्तर);
   - सत्यापित रिकॉर्ड → qtype अनुसार छाने उत्तर।

## कोडेक (RFC 1035, सख्त उपसमुच्चय)

- प्रश्न: 12-बाइट हेडर, **एक** प्रश्न, QCLASS = IN, **कोई
  संपीड़न नहीं** (संकेतक = अस्वीकृत)। लेबल lowercase और
  सत्यापित। QR=1, QDCOUNT≠1, अमान्य लेबल → **मौन**
  (कचरे की कोई लागत नहीं)।
- उत्तर: QR|RD(echo)|RA, **AA केवल प्राधिकारी उत्तरों पर**
  (चेन, ताज़ा या कैश्ड — कभी फ़ॉलबैक या त्रुटि RCODEs पर नहीं),
  प्रश्न शब्दशः कॉपी, प्राधिकारी उत्तर **RFC 1035 संपीड़ित owner**
  (प्रतिध्वनित प्रश्न में 2-बाइट संकेतक `0xC00C`) के साथ;
  फ़ॉलबैक upstream उत्तर वैसे ही सेव किए जाते हैं (कभी पुनः-एनकोड
  नहीं)।
- सेव किए प्रकार: A, AAAA, CNAME, NS, MX, TXT, **PTR, SRV, CAA**
  (+ Unknown शब्दशः पुनः-एनकोड; कुल 9 native प्रकार, rdata
  RFC अनुसार एनकोडेड — 1035/2782/8659; सख्त CAA: केवल critical bit 0x80,
  lowercase टैग)। A/AAAA प्रश्न समुच्चय के
  CNAME सम्मिलित करता है (alias chasing)। ANY प्रश्न (255): कोडेक
  द्वारा छाना पूरा समुच्चय।
- सीमाएँ (M7b): **उत्तर बजट परिवहन पर निर्भर** —
  UDP पर 512 बाइट (क्लासिक RFC 1035 §2.3.4 payload, कोई EDNS नहीं),
  TCP पर 65,535। बजट से बड़ा समुच्चय अंतिम फिट
  रिकॉर्ड पर कटा, **TC=1** के साथ (ईमानदार कर्तन, RFC 1035
  §4.2.1): क्लाइंट TCP पर पुनः प्रयास करता है (RFC 7766), जहाँ पूरा
  समुच्चय मिलता है। UDP बजट से बड़ा upstream उत्तर पुनः-एनकोड
  कर कर्तित (TC=1) होता है बजाय वैसे पहुँचाने के;
  TCP पर वह बाइट-दर-बाइट निकलता है। कर्तन कैश hits पर भी
  लागू (बजट उत्तर-समय पर, कैश-भराई पर नहीं)।
- RCODEs: 0 NOERROR (उत्तर के साथ या बिना), 2 SERVFAIL (स्थानीय
  विफलता), 3 NXDOMAIN (प्राधिकारी), 5 REFUSED (बिना upstream के
  गैर-सकोन)।

## रिकर्सिव फ़ॉलबैक

- Upstreams `addr:port` (UDP), क्रम में, प्रति
  upstream 2 s timeout, socket upstream से **connected** (कर्नेल
  फ़िल्टरिंग: किसी अन्य स्रोत का पैकेट कभी स्वीकृत नहीं)।
  Upstream उत्तर केवल तब स्वीकृत जब वह प्रश्न से **मेल खाए**:
  वही TXID, QR=1, प्रश्न (QNAME+QTYPE+QCLASS) बाइट-दर-बाइट
  कॉपी। अनुरूप न उत्तर → SERVFAIL, और कुछ भी कैश नहीं।
- सत्यापित upstream उत्तर वैसा ही पारित; उसके
  उत्तर मूल `fallback` के साथ कैश (AA कभी सेट नहीं, कैश hit पर
  भी) और TTL 600 s पर clamp। Upstream त्रुटि
  RCODEs (NOERROR/NXDOMAIN के अतिरिक्त) कैश नहीं होते।
- **डिफ़ॉल्ट रूप से निजी**: कोई upstream नहीं = सकोन आकार से
  बाहर नामों के लिए REFUSED।

## DHT निगेटिव कैश (एंटी-प्रवर्धन)

एक **अनुत्तरित DHT pull** (रिकॉर्ड ऑन-चेन अपेक्षित —
`record_hash` कमिटेड — पर स्थानीय कैश और पूछे गए पीयर में अनुपस्थित)
नाम को `DHT_NEGATIVE_TTL_SECS` (30 s) तक एक सीमित निगेटिव
कैश (FIFO, cap `DHT_NEGATIVE_CAP` = 4,096 नाम) में
खड़ा रखता है: TTL के भीतर उसी नाम के बार-बार रिज़ॉल्यूशन
**दबा दिए जाते हैं** (गिने जाते हैं, पुनः pull कभी नहीं)। कोई
स्कैनर — या हॉट नाम जिसके स्वामी ने कभी प्रकाशित नहीं किया — अब एक
DNS प्रश्न को प्रति प्रश्न प्रति mesh पीयर एक `GetRecord` में
प्रवर्धित नहीं कर सकता। निगेटिव
प्रविष्टि TTL पर, रिकॉर्ड आगमन पर (सफल pull वास्तविक
कैश में लिखता है), या FIFO cap से बाहर धकेले जाने पर मरती है।

प्रदर्शित काउंटर (`scone_dht_negative_hits_total`,
`_expired_total`, `_capped_total` — देखें "Metrics" in `relay.md`)।

## TCP (M7b, RFC 7766)

UDP जैसा ही पोर्ट (`--dns` पते पर दूसरा TCP bind)।
परिवहन RFC 1035 §4.2.2 का अनुसरण करता है: प्रत्येक संदेश के आगे
उसकी लंबाई **2 बाइट** big-endian में।

- **प्रश्न**: प्रीफ़िक्स लंबाई ≥ 1 और ≤ 512 बाइट (DNS प्रश्न
  क्लासिक payload में फिट — RFC 7766 §6; कोई EDNS सेव नहीं)। सीमा के
  बाहर → तुरंत connection बंद।
- **उत्तर**: 65,535-बाइट बजट (2-बाइट प्रीफ़िक्स अधिकतम) —
  UDP के लिए बहुत बड़ा समुच्चय यहाँ **पूरा** सेव, TC=0।
- **Pipelining**: प्रति connection कई प्रश्न क्रम से
  सीरियल सेव (एक write = एक प्रीफ़िक्स्ड उत्तर)।
- **Read timeout**: प्रति read 5 s (प्रीफ़िक्स या बॉडी) — मौन
  क्लाइंट कनेक्ट काटा जाता है, उसका स्लॉट मुक्त।
- **समवर्ती connections**: अधिकतम 64 (semaphore); 65वाँ
  तुरंत अस्वीकृत (connection बंद), कभी कतार में नहीं — tasks
  या मेमोरी का असीमित विकास नहीं।
- Read/write/timeout त्रुटियाँ: debug लॉग + साफ़ बंद। **नेटवर्क
  इनपुट पर कभी panic नहीं।**
- कचरा (अबोध प्रश्न) को मौन मिलता है पर connection
  बंद नहीं होती: अगला (वैध) प्रश्न सेव किया जाता है।

```text
client                     server
  │ [len u16][query]         │
  │ ─────────────────────►   │ cache → authoritative → fallback
  │ ◄─────────────────────   │ [len u16][response ≤ 64 KiB]
  │ (UDP had answered TC=1 → the client retries here)
```

## सीमाएँ और रेलिंग

| रेलिंग | मान |
|---|---|
| UDP डेटाग्राम (प्रश्न/उत्तर) | 4096 बाइट (आगे अस्वीकृत) |
| UDP उत्तर बजट (आगे TC=1) | 512 बाइट (कोई EDNS नहीं) |
| अधिकतम TCP प्रश्न | 512 बाइट (आगे बंद) |
| अधिकतम TCP उत्तर | 65,535 बाइट |
| समवर्ती TCP connections | 64 (semaphore, तुरंत अस्वीकृति) |
| TCP read timeout | 5 s |
| कैश | GLOBAL सीमाएँ डिफ़ॉल्ट 100,000 प्रविष्टियाँ / 64 MiB, 16 शार्ड में विभाजित (`--dns-cache-limit` / `--dns-cache-max-mem`) |
| प्राधिकारी TTL | **प्रति रिकॉर्ड** (`record.ttl`, सीमाएँ 1..=2,592,000 s; ऐतिहासिक स्थिरांक 60 s केवल सेवा उत्तरों के लिए बचा) |
| फ़ॉलबैक TTL (clamp) | 600 s |
| समानांतर UDP प्रश्न | 4,096 (`MAX_INFLIGHT_UDP`, semaphore; आगे: drop, क्लाइंट पुनः प्रयास) — ट्यूनेबल `--dns-max-inflight` (min 1) |
| DHT निगेटिव कैश | 30 s (`DHT_NEGATIVE_TTL_SECS`), FIFO cap 4,096 नाम |
| प्रति upstream timeout | 2 s |

पालित प्रोजेक्ट नियम: नेटवर्क डेटा पर कभी panic नहीं; हर जगह
सख्त डिकोडिंग; सर्वर न चेन, न store, न DHT छूता
है (रिले एकमात्र सत्यापन प्राधिकार बना रहता है)।

## GeoDNS (भौगोलिक रूटिंग)

> नॉर्मेटिव विनिर्देश। कोई भी doc/code विचलन = बग।

### एम्बेडेड GeoIP तालिका (स्वचालित)

प्रत्येक बाइनरी रिले में कंपाइल्ड एक **IP → देश mapping तालिका**
एम्बेड करती है: **कोई विन्यास ज़रूरी नहीं**, भौगोलिक रूटिंग
हर जगह स्वचालित सक्रिय।

- **डेटा स्रोत**: **RIR प्रत्यायोजन फ़ाइलें** (RIPE NCC, ARIN,
  APNIC, LACNIC, AFRINIC), मुफ़्त डाउनलोड/पुनर्वितरण योग्य:
  `https://ftp.ripe.net/pub/stats/<rir>/delegated-<rir>-extended-latest`
  (प्रत्येक प्रत्यायोजित IPv4/IPv6 ब्लॉक का पंजीकरण देश)। जनरेशन
  तिथि तालिका हेडर में
  (`assets/embedded-geo.table`)।
- **पुनर्जनन**: `scripts/gen-geo-table.py` (5
  फ़ाइलें डाउनलोड, रूपांतरण, प्रीफ़िक्स सामान्यीकरण — ~176,000 नियम)।
- **ग्रैन्युलैरिटी**: देश (numeric ISO 3166-1) + व्युत्पन्न महाद्वीप (UN
  M49)। कोई ASN या क्षेत्र नहीं (प्रत्यायोजनों में अनुपस्थित)।
- **प्रदर्शन**: क्रमबद्ध श्रेणियों पर **बाइनरी खोज**
  लुकअप (पहले उपयोग पर एक बार index, प्रति v4/v6 परिवार) — मापा
  गया ~95 ns/लुकअप हॉट, पूरी तालिका पर ~50 µs random-access
  (bench: `cargo test -p scone-network --release --test geo_bench
  -- --ignored`)।
- **रिले स्व-स्थान**: रूटिंग **प्रत्येक प्रश्न के स्रोत IP** का अनुसरण
  करती है — एक LAN रिले अपने स्थानीय क्लाइंट को सही
  zone पर स्वचालित रूट करता है।
- **प्राथमिकता**: स्पष्ट ऑपरेटर तालिका
  (`--geo-ip-table`/geo-config) एम्बेडेड को **बदल देती है**।

### अवलोकन

कोई डोमेन अपने हस्ताक्षरित रिकॉर्ड समुच्चय में **भौगोलिक रूटिंग**
नियम प्रकाशित कर सकता है: `GEOROUTE` रिकॉर्ड (सकोन निजी प्रकार
`32,768`, IANA श्रेणी से बाहर)। रिज़ॉल्वर इन डोमेनों के A/AAAA
प्रश्नों का उत्तर **नियम द्वारा चुने endpoint के पते** से देता है
(scope CLIENT की स्थिति के सबसे निकट, तालिका से उसके
स्रोत IP से व्युत्पन्न), स्थैतिक A/AAAA रिकॉर्ड के बजाय।
बाकी सब (GEOROUTE रहित डोमेन, अन्य qtypes) क्लासिक
DNS पथ **बाइट-दर-बाइट**।

### GeoDNS मेट्रिक्स

Prometheus endpoint geo उत्तर विभाजन प्रदर्शित करता है:

- `scone_dns_geo_answers_total` — कुल सेव किए GEOROUTE उत्तर;
- `scone_dns_geo_by_continent_total{continent="<M49>"}` — महाद्वीप अनुसार;
- `scone_dns_geo_by_country_total{country="<ISO>"}` — देश अनुसार
  (मानकों ही से सीमित: ≤ 9 महाद्वीप, ≤ 250
  देश)।

### GEOROUTE रिकॉर्ड (वायर)

एक GEOROUTE = एक **scope** + ≤ 32 **endpoints** (decode पर
कैननिकल क्रम: आरोही priority, अवरोही weight, आरोही target;
प्रतिकृति = अस्वीकृत):

```text
GeoScope   = 0x00 (world)
           | 0x01 continent.v (UN M49 code: AF=2, AS=142, EU=150,
                                NA=3, SA=5, OC=9, AN=999)
           | 0x02 country.v   (ISO 3166-1 numeric code: US=840,
                                TW=158, FR=250…)
           | 0x03 region.v    (OPAQUE ISO 3166-2 subdivision, u32:
                                publisher-defined number, compared
                                as is — no local table)
           | 0x04 asn.v       (AS number, u32)
           | 0x05 prefix.addr[16] || prefix.len u8
             (normalized 16-byte IP prefix: IPv4 = address in the
              first 4 bytes + ZERO tail, len ≤ 32;
              IPv6 = 16 free bytes, len ≤ 128; host bits ALWAYS
              zero — a non-normalized prefix is rejected)
GeoTarget  = 0x00 octets[4]  (binary IPv4 address)
           | 0x01 octets[16] (binary IPv6 address)
GeoEndpoint = target || priority.v || weight.v
GEOROUTE    = scope || count.v(≤32) || endpoints…
```

सत्यापन सीमाएँ (decode): `priority > 0`, `weight ≤ 100`
(`weight = 0` = निष्क्रिय endpoint, कभी निर्वाचित नहीं), TTL
किसी रिकॉर्ड की तरह 1..=2,592,000 s में। स्थानीय
तालिकाओं के लिए अज्ञात देश/महाद्वीप वायर पर **अनुमत** है: रूटिंग
सीधे उच्चतर scope पर गिर जाती है।

**वायर पश्च-संगति (v1 → v2)**: v1 बाइट्स
अपरिवर्तित — v1 scopes (world/continent/country) अपने
डिस्क्रिमिनेंट `0x00..=0x02` और सटीक एनकोडिंग रखते हैं; तीन
नए scopes अगले डिस्क्रिमिनेंट (`0x03..=0x05`) लेते हैं, कैननिकल
क्रम से मेल खाते कुल क्रम में
(`World < Continent < Country < Region < Asn < IpPrefix`)। v1
decoder `0x03` से बड़ा डिस्क्रिमिनेंट देखकर पहले से सख्ती से विफल होता था
(रिकॉर्ड अस्वीकृत); v1-निर्मित बाइट्स समान रूप से decode होते रहते
हैं (देखें `geo_known_bytes` परीक्षण, frozen)।

### चयन (रिज़ॉल्यूशन)

1. **Scope** — घटती विशिष्टता, **6 स्तर**:
   **सबसे लंबा मेल खाता IP prefix → सटीक AS → सटीक देश →
   सटीक क्षेत्र → महाद्वीप → विश्व**।
   - *IpPrefix*: जिन routes का prefix क्लाइंट के
     IP से मेल खाता है (locator के अनुसार: `client_ip`, अन्यथा
     ज्ञात origin prefixes), उनमें **सबसे लंबा** (`len` max)
     जीतता है; बराबर `len` पर, कैननिकल क्रम में पहला (`routes`
     slice का क्रम, एनकोडिंग पर क्रमबद्ध)। एक
     subdivision prefix/AS (जो सटीक नेटवर्क पहचानते हैं) से कम
     विशिष्ट और देश से भी कम (अपारदर्शी क्रमांकन, विश्वसनीय केवल
     तब यदि प्रकाशक और locator वही साझा करें), पर महाद्वीप से
     अधिक (वह अपने देश में निहित, अतः निर्विकार अपने
     महाद्वीप में)।
   - *Asn*: क्लाइंट का सटीक AS नंबर।
   - *Country*: सटीक देश।
   - *Region*: सटीक subdivision (अपारदर्शी पहचानकर्ता)।
   - *Continent*: locator द्वारा **या देश से व्युत्पन्न**
     स्थानीय तालिका से (`continent_of_country`); तालिका के
     लिए अज्ञात देश स्पष्ट
     महाद्वीप या विश्व पर गिरता है।
   - *World*।
   एक v1 [`GeoLocation`] (region/asn/prefixes/client_ip अनसेट)
   ठीक v1 व्यवहार देता है: देश → महाद्वीप →
   विश्व। कोई मेल खाता route नहीं (World scope के बिना सहित) →
   क्लासिक DNS व्यवहार, मानो GEOROUTE ही नहीं है।
2. **Priority** — SRV-जैसी semantics: केवल **न्यूनतम
   priority** समूह पात्र; उच्चतर priorities
   **failover** स्तर हैं।
3. **Weight** — निर्वाचित समूह में, **नियतिवादी भारित**
   ड्रॉ: एक nonce (रिज़ॉल्वर का प्रश्न काउंटर) का स्थायी हैश
   (SplitMix64) संचयी भारों के विरुद्ध। कोई
   RNG नहीं: वही nonce वाले दो प्रश्न वही परिणाम,
   बढ़ते nonce भारों के अनुपात में बँटते हैं।
   `weight = 0` = निष्क्रिय, कभी निर्वाचित नहीं (अकेला हो तो भी — अगले
   स्तर पर जाएँ)।
4. **Health failover** — एक **Unhealthy** endpoint अलग
   रखा जाता है; यदि पूरा न्यूनतम स्तर अनुपलब्ध, अगले
   priority स्तर पर। **अज्ञात उपलब्ध माना जाता है** (अज्ञात
   को दंड नहीं)। सब अनुपलब्ध → क्लासिक DNS
   व्यवहार।

### उत्तर

- एक अकेला पता: **IPv4 हो तो A, IPv6 हो तो AAAA** — qtype के
  अनुसार परिवार सख्त छानना (A प्रश्न कभी IPv6 का
  उत्तर नहीं देता, और उल्टा)।
- TTL = स्रोत GEOROUTE रिकॉर्ड का (decode पर सामान्य TTL
  नियमों से सीमित)।
- AA सेट (प्राधिकारी उत्तर — GEOROUTE किसी और
  हस्ताक्षरित रिकॉर्ड की तरह सत्यापित)।
- छानने के बाद खाली उत्तर (सही परिवार का कोई उम्मीदवार नहीं, सब
  Unhealthy, कोई मेल खाता route नहीं) → रिज़ॉल्वर
  अपने क्लासिक पथ पर (प्रायः NODATA: NOERROR, 0
  उत्तर); त्रुटि rcodes सामान्य नियम (कभी कैश नहीं)।
- समुच्चय में सह-अस्तित्व करता क्लासिक A/AAAA रिकॉर्ड geo से
  **पूर्व लेता है** (geo केवल तब लागू जब qtype का कोई वायर
  उत्तर अनुपस्थित)।

### कैश: स्पष्ट निर्णय

geo रूटिंग निर्णय `(qname, qtype)` के अंतर्गत **कभी कैश नहीं**
होता: वह रिज़ॉल्वर के क्लाइंट scope पर निर्भर है, और
ऐसी कुंजी TW क्लाइंट को US route दे देती। Geo उत्तर
प्रत्येक प्रश्न पर पुनर्गणित (लागत: एक select_scope + भारित
ड्रॉ, µs) और कैश को बायपास करते हैं। क्लासिक (qname, qtype) कैश
बाकी सब के लिए अपरिवर्तित — geo जब कुछ तय नहीं करता तब
उत्पन्न NODATA सहित। त्रुटि rcodes कभी कैश नहीं।

### Health checks (`--health-check`)

- प्रति लक्ष्य (`GeoTarget`) `HealthCache`: `probe` = non-blocking
  read (ताज़ा स्थिति, या Unknown), रिज़ॉल्यूशन पथ से कभी
  जाँच **ट्रिगर नहीं**।
- Refresh: यदि निर्वाचित उम्मीदवार Unknown/कैश में अनुपस्थित, एक
  refresh background task में
  (`tokio::spawn_blocking`: TCP connect blocking है,
  UDP loop में निषिद्ध)। एंटी-स्पैम: प्रति लक्ष्य एक समय एक
  refresh (HashSet), पिछला refresh समाप्त होने पर पुनः आरंभणीय।
- `TcpChecker`: `target:port` पर सीमित TCP connect (2 s
  timeout)। **पोर्ट DNS रिकॉर्ड से व्युत्पन्न नहीं
  हो सकता**: `--health-port` सेट करता है (डिफ़ॉल्ट 443)। Checker
  **जानबूझकर सरल** (सफल connect ≠ स्वस्थ
  सेवा) — प्रारूप बदले बिना सुधारणीय (HTTP, TLS, अनुप्रयोग-स्तर)।
- प्रविष्टि TTL: `--health-ttl-secs` (डिफ़ॉल्ट 5 s); समाप्त प्रविष्टि =
  Unknown = उपलब्ध।

### सुरक्षा

- GEOROUTE रिकॉर्ड किसी और हस्ताक्षरित रिकॉर्ड की तरह: किसी भी
  उपयोग से पहले चेन के विरुद्ध सत्यापित (owner, sequence,
  record_hash)। **सत्यापन के बिना कोई नेटवर्क विश्वास नहीं** —
  असत्यापित DHT GEOROUTE कभी उत्तर नहीं देता।
- क्लाइंट की स्थिति **एम्बेडेड GeoIP तालिका** (RIR
  प्रत्यायोजन, ऊपर) से उसके स्रोत IP द्वारा व्युत्पन्न — या
  रिज़ॉल्वर के स्पष्ट स्थानीय विन्यास से
  (`--geo-ip-table` या
  `--geo-country`/`--geo-continent`/`--geo-asn`/`--geo-region`,
  जो पूर्व लेता है), कभी नेटवर्क GeoIP API से नहीं (कोई
  प्रश्न रिसाव नहीं, कोई निर्भरता नहीं)।
- ड्रॉ नियतिवादी और स्थानीय: कोई रहस्य नहीं, कोई
  अप्रत्याशितता आवश्यक नहीं (सुरक्षा रिकॉर्ड
  हस्ताक्षर की है, ड्रॉ की नहीं)।

`www.example.scone` प्रकाशित करता है (apex `example.scone`, पूरा
समुच्चय प्रत्येक सबनाम की सेवा):

| Scope | Endpoint | Priority | Weight |
|---|---|---|---|
| US (840) | 10.1.0.1 | 10 | 70 |
| US (840) | 10.1.0.2 | 10 | 30 |
| US (840) | 10.2.0.1 | 20 | 100 |
| TW (158) | 10.3.0.1 | 10 | 80 |
| TW (158) | 10.4.0.1 | 10 | 20 |
| TW (158) | 10.2.0.1 | 20 | 100 |

अपेक्षित व्यवहार:

- **US** क्लाइंट → 10.1.0.1 (≈70%) या 10.1.0.2 (≈30%); दोनों
  Unhealthy → failover p20 → **10.2.0.1**;

- लागू नियम रहित डोमेन → वही प्रश्न, क्लासिक व्यवहार (NODATA:

### CLI विकल्प (`scone relay`)

| विकल्प | डिफ़ॉल्ट | भूमिका |
|---|---|---|
| (कोई नहीं — GeoDNS हमेशा चालू, एम्बेडेड तालिका) | on | स्रोत IP से स्वचालित रूटिंग |
| `--geo-ip-table <path>` | — | **स्थानीय GeoIP तालिका** (नीचे)। सभी static `--geo-*` विकल्पों पर **पूर्वता** |
| `--geo-country <u16>` | — | क्लाइंट देश, ISO 3166-1 numeric (840=US…) — static |
| `--geo-continent <u16>` | — | क्लाइंट महाद्वीप, UN M49 (150=EU…); छोड़ने पर देश से व्युत्पन्न — static |
| `--geo-asn <u32>` | — | क्लाइंट AS (64500…) — static, v2 में नया |
| `--geo-region <u32>` | — | क्लाइंट subdivision (अपारदर्शी प्रकाशक पहचानकर्ता) — static, v2 में नया |
| `--health-check` | off | जाँच सक्षम करता है (health failover) |
| `--no-health-check` | off | जाँच **स्पष्ट रूप से अक्षम** — `--health-check` पर **जीतता है** (प्राथमिकताएँ देखें) |
| `--health-ttl-secs <u64>` | 5 | health प्रविष्टि का TTL |
| `--health-port <u16>` | 443 | जाँच का TCP पोर्ट (DNS रिकॉर्ड से व्युत्पन्न नहीं) |

#### स्थानीय GeoIP तालिका (`--geo-ip-table`)

प्रीफ़िक्स की स्थानीय TEXT फ़ाइल, स्टार्टअप पर **एक बार** पढ़ी
(अधिकतम 100,000 नियम, `MAX_GEOIP_RULES`)। प्रति पंक्ति एक नियम, `#` =
टिप्पणी, खाली पंक्तियाँ उपेक्षित:

```text
# prefix/mask        country continent asn     region
10.0.0.0/8           840   3          .       .
2001:db8::/32        250   150        64500   11
192.0.2.0/24         158   9
```

- `prefix/mask`: IPv4 (`len ≤ 32`, 16-बाइट रूप में रूपांतरित,
  शून्य पूंछ — वायर जैसा संमेलन) या IPv6 (`len ≤ 128`)।
  **Host bits शून्य होने चाहिए** (`10.1.2.3/8` अस्वीकृत);
- `country`: **numeric** ISO 3166-1 `u16`, आवश्यक;
- `continent`: UN M49 `u16`, वैकल्पिक (`.` या छोड़ा = अनुपस्थित,
  महाद्वीप तब देश से व्युत्पन्न हो सकता है);
- `asn`: `u32`, वैकल्पिक (`.` = अनुपस्थित);
- `region`: अपारदर्शी `u32`, वैकल्पिक (`.` = अनुपस्थित)।

रिज़ॉल्यूशन: **DNS प्रश्न के स्रोत IP** (प्रति-क्लाइंट:
UDP `recv_from` / TCP `peer_addr`; अज्ञात → रिज़ॉल्वर का
संदर्भ IP) की तुलना 16 बाइट में; **सबसे लंबा मेल खाता prefix**
वाला नियम जीतता है (टाई पर फ़ाइल क्रम में पहला); कोई मेल नहीं →
खाली स्थिति (World)।

**सख्ती**: फ़ाइल ऑपरेटर-विन्यस्त — एक अमान्य
पंक्ति (विरूपित prefix, गैर-संख्यात्मक देश, अज्ञात महाद्वीप,
अतिरिक्त फ़ील्ड…) **offending पंक्ति संख्या लिए startup
त्रुटि** है; कभी मौन से उपेक्षित पंक्ति नहीं, कभी आंशिक
तालिका नहीं।

#### विकल्प प्राथमिकताएँ

- **Locator**: `--geo-ip-table` static विकल्पों
  (`--geo-country`/`--geo-continent`/`--geo-asn`/`--geo-region`) पर
  **पूर्वता लेता है**, जो तालिका दिए जाने पर उपेक्षित होते हैं।
  तालिका के बिना static विकल्प लागू।
- **Health**: `--no-health-check` एक **समर्पित फ़्लैग है जो
  `--health-check` पर जीतता है** — संयोजन
  `--health-check --no-health-check` जाँच बंद छोड़ता है,
  बिना इनपुट-क्रम अस्पष्टता के। `--health-check` के बिना जाँच
  डिफ़ॉल्ट रूप से बंद: **Unknown = उपलब्ध**, लक्ष्य मृत हो तो भी geo
  उत्तर निकलता है। (एक `NoopChecker` — सदा
  Healthy — भी है ताकि health संरचना बिना
  कोई endpoint अलग किए माउंट हो: परीक्षण/सतर्कता।)

उदाहरण:

```bash
scone relay --dns 127.0.0.1:5353 \
            --geo-ip-table /etc/scone/geoip.txt \
            --no-health-check
```

Static v2 उदाहरण:

```bash
scone relay --dns 127.0.0.1:5353 \
            --geo-country 250 --geo-asn 64500 --geo-region 11 \
            --health-check --health-port 443
```


## DoH / DoT (एन्क्रिप्टेड परिवहन) — बाहरी frontend द्वारा

सकोन DNS सर्वर **सादा UDP और TCP** बोलता है (RFC 1035 / 7766)
— वही native कार्यक्षेत्र है, पूर्ण और परीक्षित। *अंतिम
क्लाइंट* तक एन्क्रिप्टेड परिवहन (DoH — DNS-over-HTTPS, RFC 8484;
DoT — DNS-over-TLS, RFC 7858) एक **मानक
frontend को सौंपे गए हैं**: सकोन डेटा सेव करता है, frontend
परिवहन सेव करता है।

यह डिज़ाइन क्यों: native DoH सर्वर नोड के भीतर पूरा HTTPS
स्टैक माँगता (प्रमाणपत्र, नवीनीकरण, HTTP/2) — बड़ा
संचालन सतह, ब्राउज़र-पक्ष अंतिम उपयोगकर्ता आने से पहले शून्य
लाभ के लिए। मौजूदा frontends इसे बेहतर और अधिक समय से करते हैं;
नोड न्यूनतम रहता है।

### उदाहरण: सकोन रिले के आगे unbound से DoH

`/etc/unbound/unbound.conf`:

```
server:
    interface: 127.0.0.1
    port: 5354
    do-ip4: yes
    do-udp: no
    do-tcp: yes

    # DoH (RFC 8484) on 443
    https-port: 443
    tls-service-key: "/etc/unbound/scone.key"
    tls-service-pem: "/etc/unbound/scone.pem"

forward-zone:
    name: "."
    forward-addr: 127.0.0.1@5353   # the Scone relay (--dns 127.0.0.1:5353)
```

प्रमाणपत्र (`scone.pem`/`scone.key`) किसी TLS सेवा की तरह
प्राप्त — उदा. रिज़ॉल्वर के डोमेन पर certbot/acme.sh। DoH
क्लाइंट फिर `https://dns.example.tld/dns-query` इंगित करते हैं।

### उदाहरण: knot-resolver से DoT

`/etc/knot-resolver/kresd.conf`:

```
net.listen('127.0.0.1', 5353, { kind = 'dns' })
net.listen('0.0.0.0', 853, { kind = 'tls' })
tls.cert_file = '/etc/knot-resolver/scone.pem'
tls.key_file  = '/etc/knot-resolver/scone.key'
```

### frontend क्या जोड़ता है

- **क्लाइंट→frontend चैनल का एन्क्रिप्शन** (शत्रुतापूर्ण
  खंड: उपयोगकर्ता का नेटवर्क); frontend→relay खंड
  स्थानीय रहता है (वही मशीन या विश्वसनीय नेटवर्क)।
- **एक अतिरिक्त frontend-पक्ष कैश** (unbound/knot कैश भी —
  निर्दोष, सकोन TTL ऊपरी सीमा बने रहते हैं)।
- **एक स्थिर endpoint** (IPv4/IPv6, डोमेन) जबकि रिले घूमते रहते
  हैं।

### frontend क्या नहीं करता

- वह कुछ *सत्यापित* नहीं करता: रिले का प्रत्येक उत्तर
  कैश से पहले चेन के विरुद्ध पहले से सत्यापित ("रिज़ॉल्यूशन पथ"
  देखें)। frontend पहले-से-प्राधिकारी
  उत्तर रिले करता है।
- वह विकेंद्रीकरण का विकल्प नहीं: DoH frontend एक
  *संचालित* सेवा है — रिज़ॉल्वर ऑपरेटर का विकल्प, प्रोटोकॉल
  का नहीं। प्रत्येक सकोन रिले native UDP/TCP पर स्वतंत्र रूप से
  उपयोग योग्य रहता है।

### भावी native कार्यान्वयन (प्रलेखित, प्रतिबद्ध नहीं)

एक native DoH परिवहन (`--doh ADDR`) संभावित बना रहता है: वायर
प्रारूप समान होने से (RFC 8484 बाइनरी DNS संदेश पुनःउपयोग करता है),
वह एक TLS proxy के पीछे POST/GET decode + HTTP/2 होगा
(caddy/nginx प्रमाणपत्र सँभालते), नोड स्वयं TLS-मुक्त। कोई कार्य
प्रगति पर नहीं — माँग अंतिम उपयोगकर्ताओं के साथ आएगी।
