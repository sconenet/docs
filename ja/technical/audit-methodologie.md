# セキュリティ監査方法論 — Scone(mainnet前)

作業文書。目標:本番デプロイに向けた信頼。クレート横断の参照:AGENTS.md の厳格なルール(自作暗号なし、厳格なデコード、ハッシュ再計算、決定論)が監査の要件仕様です。

## 0. スコープと脅威(コードを再読する前に)

敵対者モデル:任意に敵対的なp2pノード(QUIC/UDP上で任意のバイトを送れる)、敵対的なtx送信者、好奇心のあるリレーオペレーター、盗まれたデータディレクトリ。設計上の除外:エンドクライアント(DNSは性質上公開)、グローバルな可用性(カオスはすでにテスト済み)。

資産表、重要度順:
1. **所有権**(状態チェーン: Register/Update/Transfer/Assign)— 誤検知 = ドメインの盗難。
2. **署名/キー保持**(keystore、Ed25519、OwnerId導出)。
3. **信頼できない入力の検証**(ワイヤーデコード、制限、パニック)。
4. **リソースDoS**(DNSキャッシュ、メモリプール、DHT、同期)。
5. **決定論/コンセンサス**(リオルグ、GC、状態の復活)。

## 1. 自動静的監査(1日目 — 機械的)

- `cargo audit`(依存関係のCVE: libp2p/quinn/rustls/redb/ed25519)。
- `cargo geiger` + `unsafe` のレビュー(期待値 ≈ 0)。
- `cargo clippy --workspace --all-targets -- -D warnings`
  (すでにグリーン。CIの壁として維持)。
- デコード境界のファジング(2〜3日目):
  `scone_protocol::decode_complete` の `cargo-fuzz`(Message、Transaction、Block、SignedDnsRecord、Checkpoint)— これが「信頼できないデータでパニックしない」が成り立つべき THE 表面です。
  予算:連続24時間のファジング、既存テストからシードしたコーパス。終了基準:クラッシュゼロ、タイムアウトゼロ、デコード分岐のカバレッジ > 95%。
- DNSワイヤーパーサー(dns.rs の `parse_query`、`extract_answers`)とレコードファイルパーサー(domain.rs)のファジング。

## 2. コンポーネントごとの対象を絞った手動レビュー(4〜8日目)

資産の重要度順。1コンポーネント = 1チェックリスト:

### 2.1 scone-crypto + 識別情報導出(4日目)
- OwnerId = BLAKE3(pubkey): バイト正準化を確認(曖昧な表現 → 2つのキー、1人の所有者は不可)。
- Ed25519: 厳格なデシリアライゼーション(非正準キーは拒否されるか?)、コンテキスト分離付きの検証(各用途が独自のドメインタグを持つ: SCONE-TX-SIG-V1、SCONE-BLOCK-V1、DHTレコード — プロトコル間のリプレイは不可能)。
- Keystore: パスフレーズ → キー(KDF? イテレーション?)、ゼロ化、ファイル権限、暗号文のパディングオラクル。

### 2.2 トランザクション適用(5日目)— 核心
各Transactionバリアント(現在13個)について:
- txはリプレイ下で冪等か(一意のtxid、nonce/シーケンス)?
- 所有権チェックはあらゆる効果に先行するか?(署名者 == オンチェーンで学習した所有者、tx自体からは決して信頼しない。)
- UpdateDomainのシーケンス: 厳密に現在+1(≥ ではない)— ギャップの拒否とリプレイの拒否を確認。
- Renew: 時間の境界(≤ 3年、> now)— 時間はBLOCKから、決してローカル時計からではない(ルールは既に設定済み、すべての呼び出し箇所を確認)。
- AssignDomain/TransferTld: 被割当者の公開鍵はすべてのパスで学習されるか(公開鍵なしプールの罠 — skill参照)。
- GC/失効: 復活は不可能か(precheck-OK/lookup-OK/push-fails のパラドックス)— gc_expired_journaled を確認。

### 2.3 ネットワーク層(6日目)
- すべてのリモートバイトは、アロケーションの前に厳格で有界なデコーダーを通るか(limits.rs の MAX_*)— 非有界な `Vec::with_capacity(input_len)` を探す。
- requery/sync GetBlocks: ピアごと、サイクルごとの境界(すでに: 128ブロック/リクエスト)— 再ダウンロードループの不在を確認。
- Gossip Record: キャッシュ/gossipの前にチェーン再検証(私のrecord_dhtテストで検証済み)— ファンアウト上限も確認。
- kad DHT: 敵対的ピアはN個のレコードの保存を強制できるか(ピアごとのクォータ?)、または正直なレコードの的を絞った追い出しは可能か?

### 2.4 DNSサーフェス(7日目)
- キャッシュ: 注入不可能(正準 (qname,qtype) キー — ケース/エンコーディングの衝突なし)、ハードなメモリバジェット(テスト済み)、フォールバックパス経由のキャッシュポイズニングなし(TXID + 質問のエコー — 上流がリモートで偽装できないことを検証)。
- 回答: 正直なAA、正直なTC、増幅なし(有界な応答/要求比 — MAX_INFLIGHT_UDP はすでに存在、TCP複製を確認)。

### 2.5 ストレージとジェネシス(8日目)
- redb: ディスク破損 → 型付きエラー、パニックなし(署名者側にはdiskfailテストが存在 — リレー側の等価物は?)。
- ジェネシス: ハッシュはマニフェスト全体をカバー。異なる2つのジェネシス = データディレクトリ拒否(テスト済み)。同期済みデータディレクトリへの事後のジェネシス注入の不可能性を検証。

## 3. 敵対テスト(9〜12日目)— 欠けているものを書く

手動レビューの各発見について、それを証明するテスト:
- シミュレーション内の敵対ノード(不正な/不一致のメッセージを送るノード付きのSimNet)— SimNetに「受動的ビザンチン」役を拡張。
- 3つの敵対ノードを含む実際の30ノードメッシュ(ランダムバイト、無効txのバースト、偽造DHTレコード)— カオスバッテリーは存在、攻撃者役を追加。
- クロスチェック: デコードの2つの実装(protocol.mdドキュメントは規範的 — 監査者がドキュメントだけからワイヤーを実装し、バイトを比較。不一致 = ドキュメントまたはコードのバグ)。

## 4. 外部監査(予算があれば)— 1〜3の後

ベンダーにとって最小の有益なスコープ: scone-crypto、scone-protocol(ワイヤー)、tx適用(state.rs)、約8〜10 k LOC。形式: 2週間、シニア暗号監査者1名 + レビュアー1名。成果物: 深刻度、PoC、レビュー済み修正を含む報告書。既存の規範的ドキュメント(docs/technical)を要件仕様の基礎として活用 — これは実際のコスト面の利点です。
