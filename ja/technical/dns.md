# UDP + TCP DNSサーバー(M6 + M7b)— `scone dns`

> SconeのDNSサーフェスの規範仕様。
> ドキュメントとコードの不一致はすべてバグです(信頼できる正しい情報源を修正すること)。

## 概要

**DNSサーバー**はリレーのオプションのサーフェスです。Scone名に対する**UDPおよびTCP** DNSクエリ(RFC 7766、同じポート)に、**チェーンに対して検証済みのデータのみから**応答し、それ以外のすべてに対しては**オプションの再帰フォールバック**(`addr:port`)を提供します。チェーンもストアもDHTも所有しません: 存在/失効の決定は**権威DNSスナップショット**(適用された各ブロックの後に公開されるRAMビュー — 下記参照)を通じて行われ、レコードの取得は内部の `RelayCommand`/`ResolveLocal` チャネル(プロセス内、1往復)を通じてリレー(プロセス)経由で行われます — CLIと同じ検証済みパスです。

```text
              UDP+TCP :5353 (default 127.0.0.1)
                    │
             scone relay --dns 127.0.0.1:5353
                    │  ┌────────────────────────────────┐
                    ├──┤ Sharded cache, 16 ways (qname)  │
                    │  └────────────────────────────────┘
                    │  Scone-shaped name?
                    │  ├─ YES → authoritative DNS snapshot:
                    │  │        unknown/expired → NXDOMAIN (RAM,
                    │  │        zero round trips into the core)
                    │  │        → apex search by suffix
                    │  │        → internal `resolve_local` (relay)
                    │  │           chain + verified record (hash,
                    │  │           owner, sequence) → answers
                    │  │        apex without a published record → NODATA
                    │  └─ NO → upstream fallback (if configured)
                    │           otherwise REFUSED
                    │
                    │  response budget:
                    │    UDP → 512 bytes (no EDNS); overflow =
                    │          cut at the last fitting record + TC=1 →
                    │          the client retries over TCP
                    │    TCP → 64 KiB (2-byte length prefix,
                    │          RFC 1035 §4.2.2): full set
```

## 起動

```bash
scone relay --dns 127.0.0.1:5353            # DNSサーフェスのみ
scone relay --dns 0.0.0.0:53 \
            --dns-upstream 1.1.1.1:53 \
            --dns-upstream 8.8.8.8:53       # + 再帰フォールバック
```

リレーは、ソケットがバインドされた時点で、実効アドレスをstdoutに通知します(`p2p:` と同様の、機械可読な契約): `dns: <addr>` 行。

検証クライアント: `dig <name> --dns 127.0.0.1:5353 --qtype A`(A、AAAA、TXT、MX、NS、CNAME、ANY)。

## 解決パス(権威 = チェーン、常に)

0. **権威DNSスナップショット**: 不変ビュー
   (`Arc<HashMap<DomainId, {valid_until, has_record}>>`、
   `tokio::sync::watch` フィード)。リレーコアが**適用された各ブロックの後**と起動時に公開します(ポーリングではなくプッシュ)。
   存在/失効の決定 — NXDOMAIN、失効ドメイン — は、このスナップショットを通じてRAMから提供されます: `Arc` のクローン1回 + マップ検索1回で、**リレーの単一所有者ランループに決して入らず**、フルパス(`RelayCommand`/`ResolveLocal`)は、実際のレコード取得(DHTプル)のために予約されたままです。キャッシュのおかげで稀です。スナップショットは決してレコードデータを運びません: 存在と失効のみです。
   - **O(タッチ分)のコピーオンライトデルタ**: マップは `Arc<HashMap>` です。チップの延長はブロックのデルタ(ブロック自身のトランザクションが、変更し得るすべてのドメインを名指しします — Register/Assign/Update/Renew/TransferDomain — 加えて、プッシュ時に評価される決定論的な失効GCの除去)を `Arc::make_mut` を通じて公開します: マップがクローンされるのは、読み取り手が前のビューをまだ保持している場合のみです。起動とリオルグはフルスナップショットを再構築します(1回のページ化バックエンド走査)。
   - 新鮮さ: 読み取り手は、ブロック適用の間、数百ミリ秒古いスナップショットを見ることがあります — 状態RPCが持つのと同じ劣化です。DNSキャッシュTTLは影響を受けません(回答はその由来に応じて権威的なまま)。
1. **シャード化キャッシュ**: [`ShardedCache`] — `hash(qname)` をキーとする16個の独立した `Cache` シャード(qtypeはシャードを共有: 名前ごとの局所性)。ホットな名前は、数千qpsで単一のミューテックスの後ろに並ぶ代わりに、トラフィックの1/16と競合します。グローバル境界(デフォルトで10万エントリ / 64 MiB、`--dns-cache-limit` / `--dns-cache-max-mem`)をシャードごとに分割(文書化された最悪ケース: 1 + N/shards の係数)。各エントリの実際のrdataサイズが計上され(エントリあたり約128バイトのオーバーヘッド)、FIFO追い出しは2つの境界のどちらかに最初に達した時点で発動 — メモリ上限は、フルサイズのエントリ(`MAX_DHT_RECORD_LEN`)に対しても維持されます。TTL 60秒(権威)/ 600秒にクランプ(フォールバック)。ネガティブキャッシュ(NXDOMAIN/NODATA)も同じルールに従い、各エントリはその由来(権威またはフォールバック)を運ぶため、ヒット時もAAビットは正直なままです。**SERVFAIL**(一時的なローカル障害)**もREFUSED**(設定状態)も決してキャッシュしません**: 両者はすべてのクエリで再計算されます。容量時のFIFO追い出し。
   **ホットパス(Cloudflare/1.1.1.1に着想)**:
   - 共有 `Arc<CacheEntry>` エントリ: ヒットは参照カウントの増加であり、rdataのディープクローンは**決して**ありません(`put` はArcを置き換えます — 共有された変異なし。TTLはシャードロックの下で引き続き検査)。
   - **アロケーションなしルックアップ**: 2レベルマップ(`Box<str>` qname → qtype → エントリ)。クエリの借用された `&str` が直接プローブします(`Borrow<str>`)— 古い `(String, u16)` タプルキーは、すべてのルックアップで新しい `String` をアロケートしていました。
   - **パックされた連続レコード**: エントリごとに1つの `Box<[u8]>` バッファー(レコードごとに `u16 rdlen ‖ u16 rtype ‖ u32 ttl ‖ rdata`)。レコードごとの `Vec` の代わりです — メモリバジェットは、アロケートされたものを正確に追跡します。
   - **出力時のRFC 1035名前圧縮**: 権威回答のオーナーは、エコーされた質問への2バイト圧縮ポインタ(`0xC00C`)です — 質問がレコードごとにフル再エンコードされることは決してありません。
2. **Scone形状?** 厳格なプレフィルター: ラベル `[a-z0-9-_]`(1..63)、≥ 2ラベル、TLD 1..63バイト `[a-z0-9-]`(`TldName::MAX_LEN` 参照)、合計長 ≤ 253 — そして**TLDがICANNルートの外側**(`is_icann_tld`、凍結されたIANAリスト + RFC 2606: `com`、`fr`、`org`… は決してSconeに属さない)。Scone名であり得ない名前(例: `www.foo_bar`、TLD内のアンダースコア)はフォールバックへ。Scone名であり得る名前(`absent.uip`)はチェーンの問題です: 未登録 → 上流がなくても権威的なNXDOMAIN。ICANN TLD(`example.com`)は、設定されていれば上流に転送、そうでなければREFUSED — Sconeが権威的に解決することは決してありません。
3. **エイペックス探索**: 接尾辞を最長から最短へ(最小2ラベル)。リレーにとってオンチェーン状態が既知である最初の接尾辞 = エイペックス。レコードセットがqname全体に応答します(サブネームを含む — 暗黙のワイルドカード動作、未決定)。
4. **`resolve_local`(内部チャネル)**: 単一の往復。DHTの待機者では決してありません。オンチェーン状態(`registered`、所有者、シーケンス、mutations)+ ローカルDHTキャッシュレコードを**再検証**(所有者、シーケンス、record_hash == オンチェーンコミットメント。レコードの署名は所有者またはレコードデリゲートから来得ます — リレーの検証と同じルール)。不適合なレコードは決して応答しません — 可用性 ≠ 権威。
   - 未登録 → NXDOMAIN。
   - 有効なレコードなしで登録済み → NODATA(NOERROR、回答0)。
   - 検証済みレコード → qtypeでフィルターされた回答。

## コーデック(RFC 1035、厳格な部分集合)

- クエリ: 12バイトヘッダー、質問は**1つ**、QCLASS = IN、**圧縮なし**(ポインタ = 拒否)。ラベルは小文字化・検証されます。QR=1、QDCOUNT≠1、無効なラベル → **沈黙**(ゴミは何の費用もかけさせません)。
- 応答: QR|RD(エコー)|RA、**権威的な回答でのみAA**(チェーン、新鮮またはキャッシュ済み — フォールバックやエラーRCODEでは決してない)、質問は逐語コピー、権威的な回答は**RFC 1035圧縮オーナー**(エコーされた質問への2バイトポインタ `0xC00C`)付き。フォールバック上流の応答はそのまま提供されます(再エンコードなし)。
- 提供される型: A、AAAA、CNAME、NS、MX、TXT、**PTR、SRV、CAA**(+ Unknownは逐語再エンコード。ネイティブ型は合計9つ、rdataはRFCに従いエンコード — 1035/2782/8659。厳格なCAA: クリティカルビット0x80のみ、小文字タグ)。A/AAAAクエリには、セットのCNAMEが含まれます(エイリアス追跡)。ANYクエリ(255): コーデックでフィルターされたセット全体。
- 制限(M7b): **応答バジェットはトランスポートに依存** — UDPでは512バイト(古典的RFC 1035 §2.3.4ペイロード、EDNSなし)、TCPでは65,535。バジェットを超えるセットは、収まる最後のレコードで切り詰められ、**TC=1**が付きます(正直な切り詰め、RFC 1035 §4.2.1): クライアントはTCPで再試行し(RFC 7766)、そこでフルセットが提供されます。UDPバジェットを超える上流の応答は、そのまま配信される代わりに再エンコードされ切り詰められます(TC=1)。TCPではバイトごとに通過します。切り詰めはキャッシュヒットにも適用されます(バジェットはキャッシュ充填時ではなく応答時に適用)。
- RCODE: 0 NOERROR(回答の有無にかかわらず)、2 SERVFAIL(ローカル障害)、3 NXDOMAIN(権威)、5 REFUSED(上流のない非Scone)。

## 再帰フォールバック

- 上流 `addr:port`(UDP)、順番に試行、上流ごとに2秒のタイムアウト、ソケットは上流に**接続済み**(カーネルフィルタリング: 他の発信元からのパケットは決して受け付けられない)。上流の応答は、それが**クエリと一致する**場合にのみ受け付けられます: 同じTXID、QR=1、質問(QNAME+QTYPE+QCLASS)がバイトごとにコピー。不適合な応答 → SERVFAIL、何もキャッシュされません。
- 検証済みの上流応答はそのまま通過します。その回答は由来 `fallback` でキャッシュされ(AAは設定されない。キャッシュヒットでも)、TTLは600秒にクランプ。上流のエラーRCODE(NOERROR/NXDOMAIN以外)はキャッシュされません。
- **デフォルトでプライベート**: 上流なし = Scone形状の外の名前に対してREFUSED。

## DHTネガティブキャッシュ(反増幅)

**未応答のDHTプル**(レコードはオンチェーンで期待されている — `record_hash` がコミット済み — が、ローカルキャッシュと問い合わせたピアに不在)は、その名前を `DHT_NEGATIVE_TTL_SECS`(30秒)の間、有界なネガティブキャッシュ(FIFO、上限 `DHT_NEGATIVE_CAP` = 4,096名)に駐車します: TTL内の同じ名前の繰り返し解決は**抑制**されます(カウントのみ、再プルなし)。スキャナー — または所有者が一度も公開していないホットな名前 — は、1つのDNSクエリをクエリごと・メッシュピアごとの `GetRecord` に増幅できなくなります。ネガティブエントリは、TTL時、レコード到着時(成功したプルは実際のキャッシュに書き込む)、またはFIFO上限からの押し出しで死にます。

公開カウンター(`scone_dht_negative_hits_total`、`_expired_total`、`_capped_total` — `relay.md` の「Metrics」参照)。

## TCP(M7b、RFC 7766)

UDPと同じポート(`--dns` アドレスへの第2のTCPバインド)。トランスポートはRFC 1035 §4.2.2に従います: すべてのメッセージは、その長さを**2バイト**ビッグエンディアンでプレフィックスされます。

- **クエリ**: プレフィックス長 ≥ 1 かつ ≤ 512バイト(DNSクエリは古典的ペイロードに収まります — RFC 7766 §6。EDNSは提供されない)。範囲外 → 即時接続切断。
- **応答**: 65,535バイトのバジェット(2バイトプレフィックスの最大)— UDPには大きすぎるセットは、ここで**完全に**提供されます。TC=0。
- **パイプライニング**: 接続ごとの複数クエリは、順番に逐次処理されます(1書き込み = 1つのプレフィックス付き応答)。
- **読み取りタイムアウト**: 読み取りごとに5秒(プレフィックスまたは本体)— 沈黙するクライアントは切断され、スロットは解放されます。
- **同時接続**: 最大64(セマフォ)。65番目は即時に拒否されます(接続切断)。キューイングはされません — タスクやメモリの非有界な増長はありません。
- 読み取り/書き込み/タイムアウトのエラー: デバッグログ + クリーンな切断。**ネットワーク入力で決してパニックしない。**
- ゴミ(解読不能なクエリ)には沈黙が返りますが、接続は切断されません: 次の(有効な)クエリが処理されます。

```text
client                     server
  │ [len u16][query]         │
  │ ─────────────────────►   │ cache → authoritative → fallback
  │ ◄─────────────────────   │ [len u16][response ≤ 64 KiB]
  │ (UDP had answered TC=1 → the client retries here)
```

## 境界とガードレール

| ガードレール | 値 |
|---|---|
| UDPデータグラム(クエリ/応答) | 4096バイト(超過は拒否) |
| UDP応答バジェット(超過でTC=1) | 512バイト(EDNSなし) |
| TCPクエリ最大 | 512バイト(超過で切断) |
| TCP応答最大 | 65,535バイト |
| 同時TCP接続 | 64(セマフォ、即時拒否) |
| TCP読み取りタイムアウト | 5秒 |
| キャッシュ | グローバル境界、デフォルトで10万エントリ / 64 MiB、16シャードに分割(`--dns-cache-limit` / `--dns-cache-max-mem`) |
| 権威TTL | **レコードごと**(`record.ttl`、境界 1..=2,592,000秒。履歴的な定数60秒は、サービス応答に対してのみ残ります) |
| フォールバックTTL(クランプ) | 600秒 |
| 並列UDPクエリ | 4,096(`MAX_INFLIGHT_UDP`、セマフォ。超過: ドロップ、クライアントが再試行)— `--dns-max-inflight` で調整可能(最小1) |
| DHTネガティブキャッシュ | 30秒(`DHT_NEGATIVE_TTL_SECS`)、FIFO上限4,096名 |
| 上流ごとのタイムアウト | 2秒 |

順守されるプロジェクトルール: ネットワークデータで決してパニックしない。いたるところで厳格なデコード。サーバーはチェーンにもストアにもDHTにも触れない(リレーが唯一の検証権威のまま)。

## 未決定事項

- EDNSなし(UDPバジェットは512バイトのまま。TC=1切り詰め + TCPがdevnetの必要をカバー)。
- レコードセットはレコードごとの名前を運ばない: セット全体が、エイペックスのすべてのサブネームに応答します(暗黙のワイルドカード)。レコードごとのアドレッシングは `DnsRecord`(プロトコル)の拡張が必要です。
- フォールバックは生のクエリを転送します: 悪意ある上流は何にでも応答でき得ます(未検証の応答 — これは標準的な再帰モデルです。Scone名がそれを通ることは決してありません)。

## GeoDNS(地理的ルーティング)

> 規範仕様。ドキュメントとコードの不一致はすべてバグです。

### 組み込みGeoIPテーブル(自動)

すべてのバイナリは、リレーにコンパイルされた**IP → 国マッピングテーブル**を組み込みます: **設定不要**で、地理的ルーティングがどこでも自動的に有効です。

- **データソース**: **DB-IP Lite**(「IP to Country Lite」)、**CC BY 4.0** ライセンス — 属性表示で再配布可能:
  `https://db-ip.com`(毎月キュレーション。以前: `scripts/gen-geo-table.py` 経由のRIR委任、削除済み)。
  量子化セル **/20 v4 と /24 v6**(DB-IPのネイティブ粒度、約130万レンジ、パーサーのメモリ上限を超過)—
  約96,500ルール。生成日はテーブルヘッダーにあります
  (`assets/embedded-geo.table`)。
- **チェックサム**: テーブルのSHA-256はコンパイル時に計算され(`build.rs`)、**起動時に再検証**されます
  (不一致 = 型付き拒否 — 改ざんされたバイナリが地理的応答を提供することは決してありません)。起動時に属性表示とともにログ出力されます。
  このハッシュは「同じビルドのすべてのノードが同じテーブルを共有する」ことを保証するもので、前提ではなく検証可能です。
- **再生成**: `scripts/geo-convert.py`(その月のDB-IP Lite CSVをダウンロード、変換 — 数値の国、ISO→M49から導出される大陸、LiteにASN/地域は不在)。
- **粒度**: 国(数値ISO 3166-1)+ 派生した大陸(UN M49)。ASNも地域もなし(Liteに不在 —
  ASN/地域のニーズは組み込みパイプラインの進化を待つものであり、ローカルテーブルは決してありません)。
- **性能**: ソート済みレンジに対する**二分探索**ルックアップ(最初の使用時にファミリーv4/v6ごとに1回構築されるインデックス)— 測定値: ホットで約95 ns/ルックアップ、フルテーブルへのランダムアクセスで約50 µs
  (ベンチ: `cargo test -p scone-network --release --test geo_bench -- --ignored`)。
- **リレーの自己位置**: ルーティングは**各クエリの送信元IP**に従います — LANリレーは、ローカルクライアントを正しいゾーンに自動的にルーティングします。
- **強制されるテーブル**(remove-geo-operator-table、2026-10-22): 組み込みテーブルが**唯一のソース**です —
  オペレーターによるインポートや上書きは存在しません。**実行時のgeoオプションは存在しません**:
  すべての `--geo-*` フラグはclapによって硬性拒否されます(geoゾーンはビルドで強制されます)。
  特定のニーズ(ASN、地域)を持つオペレーターは、組み込みパイプラインの進化を待つものであり、ローカルテーブルではありません。

### 概要

ドメインは、署名済みレコードセット内に**地理的ルーティング**ルールを公開できます: `GEOROUTE`レコード(Sconeプライベート型 `32,768`、IANA範囲外)。リゾルバーは、これらのドメインに対するA/AAAA質問に、静的なA/AAAAレコードの代わりに、**ルールが選択したエンドポイントのアドレス**(テーブル経由で送信元IPから導出された、クライアントの位置に最も近いスコープ)で応答します。その他すべて(GEOROUTEなしのドメイン、他のqtype)は、古典的なDNSパスに従い、**バイトごとに同じ**です。

### GeoDNSメトリクス

Prometheusエンドポイントはgeo回答の内訳を公開します:

- `scone_dns_geo_answers_total` — 提供されたGEOROUTE回答の合計。
- `scone_dns_geo_by_continent_total{continent="<M49>"}` — 大陸別。
- `scone_dns_geo_by_country_total{country="<ISO>"}` — 国別
  (規格自体によって有界: ≤ 9大陸、≤ 250国)。

### GEOROUTEレコード(ワイヤー)

GEOROUTE = 1つの**スコープ** + ≤ 32の**エンドポイント**(デコード時の正準ソート: 優先度昇順、重み降順、ターゲット昇順。重複 = 拒否):

```text
GeoScope   = 0x00 (world)
           | 0x01 continent.v (UN M49 code: AF=2, AS=142, EU=150,
                                NA=3, SA=5, OC=9, AN=999)
           | 0x02 country.v   (ISO 3166-1 numeric code: US=840,
                                TW=158, FR=250…)
           | 0x03 region.v    (OPAQUE ISO 3166-2 subdivision, u32:
                                publisher-defined number, compared
                                as is — no local table)
           | 0x04 asn.v       (AS number, u32)
           | 0x05 prefix.addr[16] || prefix.len u8
             (normalized 16-byte IP prefix: IPv4 = address in the
              first 4 bytes + ZERO tail, len ≤ 32;
              IPv6 = 16 free bytes, len ≤ 128; host bits ALWAYS
              zero — a non-normalized prefix is rejected)
GeoTarget  = 0x00 octets[4]  (binary IPv4 address)
           | 0x01 octets[16] (binary IPv6 address)
GeoEndpoint = target || priority.v || weight.v
GEOROUTE    = scope || count.v(≤32) || endpoints…
```

検証境界(デコード): `priority > 0`、`weight ≤ 100`(`weight = 0` = 非アクティブなエンドポイント、決して選出されない)。TTLはあらゆるレコードと同様に1..=2,592,000秒以内。ローカルテーブルが知らない国/大陸は、ワイヤー上では**許容**されます: ルーティングは、より高いスコープにフォールバックするだけです。

**ワイヤーの後方互換性(v1 → v2)**: v1のバイトは不変です — v1スコープ(world/continent/country)は判別子 `0x00..=0x02` とその厳密なエンコーディングを維持します。3つの新しいスコープは、正準ソートと一貫した全順序で続く判別子(`0x03..=0x05`)を取ります(`World < Continent < Country < Region < Asn < IpPrefix`)。判別子 ≥ `0x03` に出会ったv1デコーダーは、すでに厳格に失敗していました(レコード拒否)。v1が生成したバイトは同一にデコードされ続けます(`geo_known_bytes` テスト参照、凍結)。

### 選出(解決)

1. **スコープ** — 特異性の減少、**6レベル**:
   **最長一致IPプレフィックス → 完全一致AS → 完全一致国 → 完全一致地域 → 大陸 → ワールド**。
   - *IpPrefix*: クライアントのIPにプレフィックスが一致するルートのうち(ロケーターが知るもの: `client_ip`、さもなければ既知の発信元プレフィックス)、**最長**(`len` 最大)が勝ちます。`len` が等しければ、正準順の最初(エンコード時にソートされた `routes` スライスの順序)。細分地域は、プレフィックス/AS(正確なネットワークを特定する)よりも特異性が低く、国(不透明な番号付け、パブリッシャーとロケーターが同じものを共有する場合にのみ信頼できる)よりも低いですが、大陸(その国に含まれ、したがってその大陸にも当然含まれる)よりも高いです。
   - *Asn*: クライアントの完全なAS番号。
   - *Country*: 完全な国。
   - *Region*: 完全な細分地域(不透明な識別子)。
   - *Continent*: ロケーターが提供、**または**ローカルテーブル経由で国から導出(`continent_of_country`)。テーブルに未知の国は、明示的な大陸またはワールドにフォールバック。
   - *World*。
   v1 [`GeoLocation`](地域/asn/prefixes/client_ip未設定)は、ちょうどv1の動作を生成します: 国 → 大陸 → ワールド。一致するルートなし(ワールドスコープなしを含む)→ GEOROUTEが存在しないかのような古典的DNS動作。
2. **優先度** — SRV類似の意味論: **最小優先度**のグループのみが適格。より高い優先度は**フェイルオーバー**レベルです。
3. **重み** — 選出されたグループ内で、**決定論的な重み付き**抽選: ノンス(リゾルバーのクエリカウンター)の安定ハッシュ(SplitMix64)を累積重みに対して適用。RNGなし: 同じノンスの2つのクエリは同じ結果を与え、増加するノンスは重みに比例して分散します。`weight = 0` = 非アクティブ、決して選出されない(単独でも — 次のレベルへ移動)。
4. **署名順、ゼロプロービング** — リゾルバーはエンドポイントの可用性を**決して**判定しません:
   選出されたスコープのすべてのアクティブなエンドポイント(weight > 0)が候補となり、
   最小レベルの先頭が重み付き抽選で選出され、続くものが**署名済みレコードセット順**で
   フェイルオーバーとして機能します(順序こそがフェイルオーバー機構です)。
   エンドポイントの到達可能性はエンドポイントオペレーターの関心事であり、リゾルバーのものでは決してありません。

### 応答

- 単一のアドレス: **IPv4ならA、IPv6ならAAAA** — qtypeに従うファミリーによる厳格なフィルタリング(Aの質問にIPv6で応答することは決してなく、その逆も同様)。
- TTL = 元のGEOROUTEレコードのもの(一般的なTTLルールによってデコード時に有界)。
- AA設定(権威ある応答 — GEOROUTEは他と同様に検証済みの署名レコードです)。
- フィルタリング後の空の応答(正しいファミリーの候補なし、そのゾーンのルートなし)→ リゾルバーは古典的パスを続行します(典型的にはNODATA: NOERROR、回答0)。エラーrcodeは一般ルールに従います(決してキャッシュされない)。
- セット内に共存する古典的なA/AAAAレコードは、geoより**優先**します(geoは、qtypeに対するワイヤー回答がない場合にのみ適用)。

### キャッシュ: 明示的な決定

geoルーティングの決定は、`(qname, qtype)` の下で**決してキャッシュされません**: それはリゾルバーのクライアントスコープに依存し、そのようなキーはTWクライアントにUSルートを提供してしまうでしょう。geo回答はすべてのクエリで再計算され(コスト: 1回のselect_scope + 重み付き抽選、µs)、キャッシュをバイパスします。古典的な(qname、qtype)キャッシュは、その他すべてに対して変更なしのままです — geoが何も決定しないときに生成されるNODATAを含めて。エラーrcodeは引き続きキャッシュされません。

### NS委任(`ns` レコード)— 所有者が誰にサービスさせるかを選ぶ

ドメインの所有者が、ドメインごとにサービスモードを選択します:

- **DHT(デフォルト)** — NSレコードがなければ、SconeネットワークがオンチェーンのA/AAAAに応えます
  (リレーの `--dns`、またはエクスポート経由のNSDブリッジ);
- **独立NS** — 所有者が `ns <ip-or-name>` レコードを追加します(彼ら自身のネームサーバー、
  直接IPまたはホスト名): ドメインは**委任**されます — ネットワークはそのコンテンツの提供を止め
  (A/AAAA → NODATA + NS権威)、解決する者は誰でも所有者のNSに従います。上限:
  **ドメインごとに12個の重複のないNS**(すべての形式、値で重複排除 — 実際のレジストリの上限を反映)。
  NSを1つ削除するとスロットが解放され、すべて削除するとDHTモードに戻ります。

**ヘルスチェックは存在しません**: エンドポイントの可用性はエンドポイントオペレーターの関心事です —
リゾルバーは署名済みレコードセットをレコード順のまま提供します(レコード順こそがフェイルオーバー機構です)。

### セキュリティ

- GEOROUTEレコードは他と同様の署名済みレコードです: あらゆる使用の前にチェーンに対して検証されます(所有者、シーケンス、record_hash)。**検証なしのネットワーク信頼はなし** — 未検証のDHT GEOROUTEは決して応答しません。
- クライアントの位置は**自動発見された経路**から来ます: リレーはその外部アドレス(STUN/AutoNAT/
  UPnP)をビルドで強制された組み込みテーブルで解決して自己位置を特定します — LANクライアント
  (プライベート送信元IP)はその位置を継承し、インターネットクライアントは自身のIPで解決され、
  未知はワールドにフォールバックします。ネットワークGeoIP APIからは決して(クエリ漏洩なし、依存関係なし)、
  オペレーターの宣言からも決してありません(ゾーンはビルドで強制されます)。
- 抽選は決定論的かつローカルです: 秘密なし、予測不可能性は不要(セキュリティはレコード署名のものであり、抽選のものではない)。

### 完全な例(参照仕様)

`www.example.scone` が公開します(エイペックス `example.scone`、セット全体がすべてのサブネームに応答):

| スコープ | エンドポイント | 優先度 | 重み |
|---|---|---|---|
| US (840) | 10.1.0.1 | 10 | 70 |
| US (840) | 10.1.0.2 | 10 | 30 |
| US (840) | 10.2.0.1 | 20 | 100 |
| TW (158) | 10.3.0.1 | 10 | 80 |
| TW (158) | 10.4.0.1 | 10 | 20 |
| TW (158) | 10.2.0.1 | 20 | 100 |
| WORLD | 10.0.0.1 | 100 | 100 |

期待される動作:

- **US**クライアント → 10.1.0.1(約70%)または 10.1.0.2(約30%)。p20レベルに到達するのは、
  アクティブなp10エンドポイントが1つもない場合(weight = 0 が everywhere)のみ → そのとき **10.2.0.1**。
- **TW**クライアント → 10.3.0.1(約80%)または 10.4.0.1(約20%)。
- **FR**クライアント(250)→ セットにFRもEUルートもなし → WORLD → **10.0.0.1**。
- IPv6のみのルートへの **A** 質問 → 空の応答(AにIPv6は決して入らない)。
- 適用可能なルールのないドメイン → 同じ質問、古典的動作(NODATA: GEOROUTEにはワイヤーA rdataがない)。

### CLIオプション(`scone relay`)

| オプション | デフォルト | 役割 |
|---|---|---|
| (なし — GeoDNS常時有効、組み込みテーブル) | 有効 | 送信元IPによる自動ルーティング |
| `--geo-ip-table`、`--geo-config`、`--geo-country/…`、`--health-*` | — | (削除済み — ハードブレイク: geoゾーンはビルドで強制され、リゾルバーはヘルスチェックを一切行いません。実行時フラグは存在しません) |

#### 組み込みテーブルが唯一のソース

GeoIPテーブルは**ビルドで強制**されます(DB-IP Lite、量子化 — 上記の組み込みテーブルの節を参照):
オペレーターテーブルをインポートすることはできません。解決: **DNSクエリの送信元IP**
(クライアントごと: UDP `recv_from` / TCP `peer_addr`)が組み込みテーブルに対して16バイトで比較され、
**最長一致プレフィックス**を持つルールが勝ちます(同点なら、ファイル順の最初)。

- **プライベート/ルーティング不可の送信元**(RFC1918、ULA fc00::/7、リンクローカル、ループバック):
  クライアントはリレーのネットワークの内側にいます — リレー自身が発見した位置を継承します;
- **テーブルに存在しない公開送信元**: ワールド(geo分割なし — 誤った応答は決してしません)。

**厳格さ**は将来のいかなるテーブルサーフェスのためにも保持されます: 無効な行は問題の行番号を伴う
型付き起動エラーです。黙って無視される行も、部分的なテーブルも決してありません。

#### オプションの優先順位

- **ロケーター**: 組み込みテーブルが地理位置を**強制**します — オペレーターによる上書きはありません。
  リレーは外部アドレスからその位置を発見し(STUN/AutoNAT/UPnPをテーブルで解決)、LANクライアントは
  その位置を継承し、インターネットクライアントは送信元IPで解決され、未知はワールドにフォールバックします。

例(geoフラグなしでgeoルーティングは有効):

```bash
scone relay --dns 127.0.0.1:5353
```


## DoH / DoT(暗号化トランスポート)— 外部フロントエンド経由

Scone DNSサーバーは**平文のUDPとTCP**(RFC 1035 / 7766)を話します — それがネイティブのスコープであり、完全かつテスト済みです。*エンドクライアント*への暗号化トランスポート(DoH — DNS-over-HTTPS、RFC 8484。DoT — DNS-over-TLS、RFC 7858)は、**標準的なフロントエンドに委任**されます: Sconeがデータを提供し、フロントエンドがトランスポートを提供します。

この設計の理由: ネイティブなDoHサーバーは、ノード内に完全なHTTPSスタック(証明書、更新、HTTP/2)を必要とします — ブラウザ側のエンドユーザーが現れる前には利益ゼロの、大きな運用サーフェスです。既存のフロントエンドのほうが、より長く、より上手にやります。ノードは最小限に留まります。

### 例: Sconeリレーの前でDoHを行うunbound

`/etc/unbound/unbound.conf`:

```
server:
    interface: 127.0.0.1
    port: 5354
    do-ip4: yes
    do-udp: no
    do-tcp: yes

    # DoH (RFC 8484) on 443
    https-port: 443
    tls-service-key: "/etc/unbound/scone.key"
    tls-service-pem: "/etc/unbound/scone.pem"

forward-zone:
    name: "."
    forward-addr: 127.0.0.1@5353   # the Scone relay (--dns 127.0.0.1:5353)
```

証明書(`scone.pem`/`scone.key`)は、あらゆるTLSサービスと同様に取得します — 例えばリゾルバーのドメイン上のcertbot/acme.sh。DoHクライアントは `https://dns.example.tld/dns-query` を指します。

### 例: DoTを行うknot-resolver

`/etc/knot-resolver/kresd.conf`:

```
net.listen('127.0.0.1', 5353, { kind = 'dns' })
net.listen('0.0.0.0', 853, { kind = 'tls' })
tls.cert_file = '/etc/knot-resolver/scone.pem'
tls.key_file  = '/etc/knot-resolver/scone.key'
```

### フロントエンドが追加するもの

- **クライアント→フロントエンドチャネルの暗号化**(敵対的な区間: ユーザーのネットワーク)。フロントエンド→リレー区間はローカルのまま(同じマシンまたは信頼されたネットワーク)。
- **フロントエンド側の追加キャッシュ**(unbound/knotのキャッシュも — 無害。SconeのTTLが上限のまま)。
- **安定したエンドポイント**(IPv4/IPv6、ドメイン)。リレーが移動しても。

### フロントエンドがしないこと

- 何も*検証*しません: リレーが提供するすべての回答は、キャッシュされる前にチェーンに対してすでに検証済みです(「解決パス」参照)。フロントエンドは、すでに権威的な回答を中継します。
- 分散化を代替しません: DoHフロントエンドは*運用された*サービスです — リゾルバー運用者の選択であり、プロトコルのものではありません。すべてのSconeリレーは、ネイティブなUDP/TCP上で独立して利用可能なままです。

### 将来のネイティブ実装(文書化済み、コミット未定)

ネイティブなDoHトランスポート(`--doh ADDR`)は考えられ得るままです: ワイヤーフォーマットが同一であるため(RFC 8484はバイナリDNSメッセージを再利用)、それはPOST/GETデコード + TLSプロキシの背後のHTTP/2となり(証明書を処理するcaddy/nginx)、ノード自身はTLSフリーに留まります。進行中の作業はありません — 需要はエンドユーザーとともに来るでしょう。
