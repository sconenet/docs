# Методология аудита безопасности — Scone (перед mainnet)

Рабочий документ. Цель: уверенность для развёртывания в продакшен.
Перекрёстные ссылки: жёсткие правила AGENTS.md (никакой
самодельной криптографии, строгое декодирование, перевычисление
хешей, детерминизм) являются спецификацией требований аудита.

## 0. Объём и угрозы (до перечитывания какой-либо строки кода)

Модель противника: произвольно враждебный p2p-узел (может отправить
любые байты по QUIC/UDP), враждебный отправитель tx, любопытный
оператор реле, украденный data-dir. ИСКЛЮЧЕНО по построению:
конечный клиент (DNS по своей природе публичен), глобальная
доступность (хаос уже протестирован).

Таблица активов, в порядке критичности:
1. **Владение** (цепочка состояния: Register/Update/Transfer/Assign)
   — ложное срабатывание = кража домена.
2. **Подпись/владение ключом** (keystore, Ed25519, вычисление
   OwnerId).
3. **Валидация недоверенного ввода** (декодирование wire, лимиты,
   паники).
4. **DoS на ресурсы** (DNS-кэш, мемпул, DHT, синхронизация).
5. **Детерминизм/консенсус** (реорг, GC, воскрешение состояния).

## 1. Автоматизированный статический аудит (день 1 — механика)

- `cargo audit` (CVE зависимостей: libp2p/quinn/rustls/redb/ed25519).
- `cargo geiger` + ревью `unsafe` (ожидается ≈ 0).
- `cargo clippy --workspace --all-targets -- -D warnings`
  (уже зелёный, держать как барьер CI).
- Фаззинг границ декодирования (дни 2-3):
  `cargo-fuzz` на `scone_protocol::decode_complete` (Message,
  Transaction, Block, SignedDnsRecord, Checkpoint) — это ТА
  поверхность, где должно выполняться «никогда не паниковать на
  недоверенных данных». Бюджет: 24 ч непрерывного фаззинга, корпус
  засеян из существующих тестов. Критерий выхода: нуль крашей,
  нуль таймаутов, покрытие ветвей декодирования > 95%.
- Фаззинг парсера DNS wire (dns.rs `parse_query`,
  `extract_answers`) и парсера файла записей (domain.rs).

## 2. Целевое ручное ревью по компонентам (дни 4-8)

Упорядочено по критичности активов, 1 компонент = 1 чеклист:

### 2.1 scone-crypto + выведение идентичности (день 4)
- OwnerId = BLAKE3(pubkey): проверить канонизацию байт (никакой
  неоднозначной репрезентации → 2 ключа, 1 владелец).
- Ed25519: строгая ДЕСЕРИАЛИЗАЦИЯ (неканонический ключ
  отклоняется?), проверка с разделением контекстов (у каждого
  использования свой тег домена: SCONE-TX-SIG-V1, SCONE-BLOCK-V1,
  DHT-запись — кросс-протокольный replay невозможен).
- Keystore: парольная фраза → ключ (KDF? итерации?), обнуление,
  права на файл, padding oracle на шифртексте.

### 2.2 Применение транзакций (день 5) — ядро
Для КАЖДОГО варианта Transaction (сегодня 13):
- Идемпотентна ли tx при replay (уникальный txid, nonce/
  последовательность)?
- Предшествует ли проверка владения любому эффекту? (подписант ==
  владелец, выученный из цепочки, никогда не доверяется из самой
  tx.)
- UpdateDomain sequence: ровно current+1 (а не ≥) — проверить
  отклонение пропусков и отклонение replay.
- Renew: временные границы (≤ 3 лет, > now) — время берётся из
  БЛОКА, никогда из локальных часов (правило уже установлено,
  проверить каждую точку вызова).
- AssignDomain/TransferTld: выучивается ли pubkey получателя
  (ловушка пула без pubkey — см. skill) на всех путях.
- GC/истечение: воскрешение невозможно (парадокс
  precheck-OK/lookup-OK/push-fails) — проверить
  gc_expired_journaled.

### 2.3 Сетевой слой (день 6)
- Каждый удалённый байт проходит через строгий ограниченный
  декодер ДО аллокации (MAX_* из limits.rs) — искать неограниченный
  `Vec::with_capacity(input_len)`.
- requery/sync GetBlocks: границы на пира и на цикл (уже: 128
  блоков/запрос) — проверить отсутствие циклов повторной загрузки.
- Gossip Record: повторная проверка по цепочке ДО кэша/гossip
  (проверено моими тестами record_dht) — проверить также потолок
  fanout.
- kad DHT: может ли враждебный пир принудить к хранению N записей
  (квота на пира?) или адресное вытеснение честных записей?

### 2.4 DNS-поверхность (день 7)
- Кэш: инъекция невозможна (канонический ключ (qname,qtype) —
  никаких коллизий регистра/кодировки), жёсткий бюджет памяти
  (протестирован), никакого отравления кэша через путь фолбэка
  (TXID + эхо вопроса — проверить, что upstream нельзя подделать
  удалённо).
- Ответы: честный AA, честный TC, без усиления (ограниченное
  отношение ответ/запрос — MAX_INFLIGHT_UDP уже есть, проверить
  репликацию на TCP).

### 2.5 Хранилище и генезис (день 8)
- redb: повреждение диска → типизированная ошибка, без паники
  (тест diskfail существует на стороне подписанта — эквивалент
  на реле?).
- Генезис: хеш покрывает весь манифест; два разных генезиса =
  отказ data-dir (протестировано); проверить невозможность
  внедрить генезис ЗАДНИМ ЧИСЛОМ на синхронизированном data-dir.

## 3. Тесты противника (дни 9-12) — написать недостающее

Для каждой находки ручного ревью — тест, который её доказывает:
- враждебный узел в симуляции (SimNet с узлом, отправляющим
  некорректные/несогласующиеся сообщения) — расширить SimNet
  ролью «пассивный византиец»;
- реальная сеть из 30 узлов с 3 враждебными (случайные байты,
  всплески невалидных tx, поддельные DHT-записи) — батарея хаоса
  существует, добавить роль атакующего;
- перекрёстные проверки: две реализации декодирования (документ
  protocol.md НОРМАТИВЕН — аудитор реализует wire ТОЛЬКО по
  документу и сравнивает байты; любое расхождение = баг документа
  ИЛИ кода).

## 4. Внешний аудит (если есть бюджет) — после 1-3

Минимальный выгодный объём для вендора: scone-crypto,
scone-protocol (wire), применение tx (state.rs), ~8-10 k LOC.
Формат: 2 недели, 1 старший криптоаудитор + 1 ревьюер. Результат:
отчёт с серьёзностью, PoC, проверенные исправления. Опираться
на существующую нормативную документацию (docs/technical) как
на основу спецификации требований — это реальное ценовое
преимущество.

## 5. Критерии выхода (go/no-go mainnet)

- [ ] cargo-fuzz 24 ч без крашей на 5 декодерах
- [ ] Ревью 2.2 завершено: у каждого варианта tx есть свой лист
      (владение/replay/время/эффекты), подписанный ревьюером
- [ ] Сеть из 30 узлов, включая враждебные: 48 ч без расхождения
      типa или порчи кэша
- [ ] Расхождение документации/кода: нуль (проверено двойной
      реализацией wire)
- [ ] Блокирующие CVE: нуль (cargo audit)
- [ ] Внешний аудит объёма crypto/wire/tx выполнен (если
      запланирован)

## Рекомендуемый порядок выполнения

1→2.1→2.2 (ядро, 60% риска)→2.3→2.4→2.5→3 параллельно с каждым
ревью (тест противника пишется в день находки, а не после).
