# DNS-сервер UDP + TCP (M6 + M7b) — `scone dns`

> Нормативная спецификация DNS-поверхности Scone. Любое
> расхождение документации с кодом = баг (исправить источник
> истины).

## Обзор

**DNS-сервер** — опциональная поверхность реле: он отвечает
на DNS-запросы **UDP и TCP** (RFC 7766, тот же порт) для имён
Scone **только по данным, проверенным против цепочки**, и
предлагает **опциональный рекурсивный фолбэк** (`addr:port`) для
всего остального. Он не владеет ни цепочкой, ни хранилищем, ни
DHT: решения о существовании/истечении проходят через
**авторитетный DNS-снапшот** (ОЗУ-представление, публикуемое
после каждого применённого блока — см. ниже), а получение записей
— через реле (процесс), по внутреннему каналу
`RelayCommand`/`ResolveLocal` (внутрипроцессно, один раунд) — тот
же проверенный путь, что и CLI.

```text
              UDP+TCP :5353 (default 127.0.0.1)
                    │
             scone relay --dns 127.0.0.1:5353
                    │  ┌────────────────────────────────┐
                    ├──┤ Sharded cache, 16 ways (qname)  │
                    │  └────────────────────────────────┘
                    │  Scone-shaped name?
                    │  ├─ YES → authoritative DNS snapshot:
                    │  │        unknown/expired → NXDOMAIN (RAM,
                    │  │        zero round trips into the core)
                    │  │        → apex search by suffix
                    │  │        → internal `resolve_local` (relay)
                    │  │           chain + verified record (hash,
                    │  │           owner, sequence) → answers
                    │  │        apex without a published record → NODATA
                    │  └─ NO → upstream fallback (if configured)
                    │           otherwise REFUSED
                    │
                    │  response budget:
                    │    UDP → 512 bytes (no EDNS); overflow =
                    │          cut at the last fitting record + TC=1 →
                    │          the client retries over TCP
                    │    TCP → 64 KiB (2-byte length prefix,
                    │          RFC 1035 §4.2.2): full set
```

## Запуск

```bash
scone relay --dns 127.0.0.1:5353            # DNS surface only
scone relay --dns 0.0.0.0:53 \
            --dns-upstream 1.1.1.1:53 \
            --dns-upstream 8.8.8.8:53       # + recursive fallback
```

Реле объявляет действующий адрес в stdout (машиночитаемый
контракт, как `p2p:`): строка `dns: <addr>`, как только сокет
привязан.

Клиент валидации: `dig <name> --dns 127.0.0.1:5353 --qtype A`
(A, AAAA, TXT, MX, NS, CNAME, ANY).

## Путь разрешения (АВТОРИТЕТ = цепочка, всегда)

0. **Авторитетный DNS-снапшот**: неизменяемое представление
   (`Arc<HashMap<DomainId, {valid_until, has_record}>>`,
   канал `tokio::sync::watch`), публикуемое ядром реле **после
   каждого применённого блока** (push, не poll) и при загрузке.
   Решения о существовании/истечении — NXDOMAIN, истёкший домен —
   обслуживаются из ОЗУ через этот снапшот: одно клонирование
   `Arc` + один поиск в карте, **никогда не входя в
   одновладельческий цикл событий реле**. Полный путь
   (`RelayCommand`/`ResolveLocal`) остаётся зарезервированным
   для фактических получений записей (DHT-пуллы), редких
   благодаря кэшу. Снапшот НИКОГДА не несёт данных записей:
   только существование и истечение.
   - **Копи-он-райт дельты O(тронуто)**: карта — `Arc<HashMap>`;
     расширение типa публикует дельту блока (собственные
     транзакции блока называют каждый домен, который они могут
     изменить — Register/Assign/Update/Renew/TransferDomain —
     плюс детерминированные удаления GC истечений, вычисленные
     при push) через `Arc::make_mut`: карта клонируется ТОЛЬКО
     если читатель ещё держит предыдущее представление. Загрузка
     и реорги перестраивают полный снапшот (один пагинированный
     обход бэкенда).
   - Свежесть: читатель может увидеть снапшот возрастом в
     несколько сотен мс во время применения блока — та же
     отсталость, что был бы у статусного RPC; TTL DNS-кэша не
     затронуты (ответы остаются авторитетными по своему
     происхождению).
1. **Сегментированный кэш**: [`ShardedCache`] — 16 независимых
   сегментов `Cache`, ключ — `hash(qname)` (qtype разделяет
   сегмент: локальность по имени). Горячее имя соперничает
   с 1/16 трафика вместо очереди за одним мьютексом на тысячах
   qps. ГЛОБАЛЬНЫЕ границы (100 000 записей / 64 МиБ по
   умолчанию, `--dns-cache-limit` / `--dns-cache-max-mem`)
   делится по сегментам (задокументированный худший случай:
   множитель 1 + N/сегментов). РЕАЛЬНЫЙ размер rdata каждой
   записи учитывается (~128 байт накладных на запись), и
   FIFO-вытеснение срабатывает по первой из двух достигнутых
   границ — потолок памяти держится даже против полноразмерных
   записей (`MAX_DHT_RECORD_LEN`). TTL 60 с (авторитетно) /
   ограничен 600 с (фолбэк). Отрицательный кэш
   (NXDOMAIN/NODATA) следует тем же правилам; каждая запись
   несёт своё происхождение (авторитетное или фолбэк), чтобы бит
   AA оставался честным при попадании. **Никогда не кэшировать
   SERVFAIL** (временный локальный сбой) **ни REFUSED**
   (состояние конфигурации): оба перевычисляются на каждый
   запрос. FIFO-вытеснение при заполнении. **Горячий путь
   (вдохновлено Cloudflare/1.1.1.1)**:
   - разделяемые записи `Arc<CacheEntry>`: попадание —
     увеличение счётчика ссылок, НИКОГДА глубокое клонирование
     rdata (`put` ЗАМЕНЯЕТ Arc — никакой разделённой мутации;
     TTL всё равно проверяется под блокировкой сегмента);
   - **поиск без аллокаций**: двухуровневая карта
     (`Box<str>` qname → qtype → запись), заимствованный `&str`
     запроса пробует напрямую (`Borrow<str>`) — старый ключ-
     кортеж `(String, u16)` аллоцировал свежую `String` на
     КАЖДЫЙ поиск;
   - **упакованные смежные записи**: один буфер `Box<[u8]>` на
     запись (`u16 rdlen ‖ u16 rtype ‖ u32 ttl ‖ rdata` на
     запись) вместо одного `Vec` на запись — бюджет памяти
     отслеживает ровно то, что аллоцировано;
   - **сжатие имён RFC 1035 на выводе**: владелец авторитетных
     ответов — 2-байтовый указатель сжатия (`0xC00C`) в
     отражённый вопрос — вопрос никогда не перекодируется
     целиком на каждую запись.
2. **Форма Scone?** Строгий пре-фильтр: метки `[a-z0-9-_]`
   (1..63), ≥ 2 метки, TLD 1..63 байта `[a-z0-9-]` (см.
   `TldName::MAX_LEN`), общая длина ≤ 253 — **и TLD вне корня
   ICANN** (`is_icann_tld`, замороженный список IANA + RFC 2606:
   `com`, `fr`, `org`… никогда не принадлежат Scone). Имя, которое
   НЕ МОЖЕТ быть именем Scone (например, `www.foo_bar`,
   подчёркивание в TLD), идёт во фолбэк; возможное имя Scone
   (`absent.uip`) — дело цепочки: незарегистрировано →
   авторитетный NXDOMAIN, даже без upstream. TLD ICANN
   (`example.com`) перенаправляется к upstream'ам, если
   настроены, иначе REFUSED — никогда не разрешается
   авторитетно Scone.
3. **Поиск апекса**: суффиксы от самого длинного к самому
   короткому (мин. 2 метки). Первый суффикс, чьё состояние
   в цепочке известно реле, — апекс; набор записей обслуживает
   всё qname (подимена включены — неявное поведение дикого
   знака, открытое решение).
4. **`resolve_local` (внутренний канал)**: один раунд, никогда
   ожидание DHT. Состояние в цепочке (`registered`, владелец,
   sequence) + локальная кэш-запись DHT **перепроверена**
   (владелец, sequence, record_hash == обязательательство
   в цепочке). Неконформная запись никогда не отвечает —
   доступность ≠ авторитетность.
   - незарегистрировано → NXDOMAIN;
   - зарегистрировано без валидной записи → NODATA (NOERROR,
     0 ответов);
   - проверенная запись → ответы, отфильтрованные по qtype.

## Кодек (RFC 1035, строгое подмножество)

- Запрос: заголовок 12 байт, **один** вопрос, QCLASS = IN,
  **без сжатия** (указатель = отказ). Метки в нижнем регистре
  и валидированы. QR=1, QDCOUNT≠1, некорректные метки →
  **молчание** (мусор ничего не стоит).
- Ответ: QR|RD(эхо)|RA, **AA только на авторитетных ответах**
  (цепочка, свежих или кэшированных — никогда на фолбэке и
  не на RCODE ошибок), вопрос скопирован дословно,
  авторитетные ответы с **сжатым по RFC 1035 владельцем**
  (2-байтовый указатель `0xC00C` в отражённый вопрос); ответы
  upstream фолбэка отдаются как есть (никогда не
  перекодируются).
- Обслуживаемые типы: A, AAAA, CNAME, NS, MX, TXT, **PTR, SRV,
  CAA** (+ Unknown перекодируется дословно; 9 нативных типов
  всего, rdata кодируется по RFC — 1035/2782/8659; строгий CAA:
  только критический бит 0x80, метки в нижнем регистре). Запрос
  A/AAAA включает CNAME набора (погоня за псевдонимами). Запрос
  ANY (255): весь набор, отфильтрованный кодеком.
- Ограничения (M7b): **бюджет ответа зависит от транспорта** —
  512 байт по UDP (классическая полезная нагрузка RFC 1035
  §2.3.4, без EDNS), 65 535 по TCP. Набор, превышающий бюджет,
  режется на последней помещающейся записи, с **TC=1** (честное
  усечение, RFC 1035 §4.2.1): клиент повторяет по TCP
  (RFC 7766), где отдаётся полный набор. Ответ upstream больше
  UDP-бюджета перекодируется усечённым (TC=1) вместо отдачи как
  есть; по TCP проходит байт в байт. Усечение применяется и к
  попаданиям кэша (бюджет применяется в момент ответа, а не
  заполнения кэша).
- RCODE: 0 NOERROR (с ответами или без), 2 SERVFAIL (локальный
  сбой), 3 NXDOMAIN (авторитетно), 5 REFUSED (не-Scone без
  upstream).

## Рекурсивный фолбэк

- Upstream'ы `addr:port` (UDP), пробуются по порядку, таймаут
  2 с на upstream, сокет **соединён** с upstream (фильтрация
  ядром: пакет от любого другого источника никогда не
  принимается). Ответ upstream принимается, только если он
  **соответствует запросу**: тот же TXID, QR=1, вопрос
  (QNAME+QTYPE+QCLASS) скопирован байт в байт. Неконформный
  ответ → SERVFAIL, и ничего не кэшируется.
- Проверенный ответ upstream передаётся как есть; его ответы
  кэшируются с происхождением `fallback` (AA никогда не
  ставится, даже при попадании в кэш) и TTL, ограниченным
  600 с. RCODE ошибок upstream (кроме NOERROR/NXDOMAIN) не
  кэшируются.
- **Приватность по умолчанию**: без upstream = REFUSED для имён
  вне формы Scone.

## Отрицательный кэш DHT (анти-усиление)

**Неотвеченный DHT-пулл** (запись ожидается в цепочке —
`record_hash` закреплён — но отсутствует в локальном кэше
и у опрошенных пиров) паркует имя на `DHT_NEGATIVE_TTL_SECS`
(30 с) в ограниченном отрицательном кэше (FIFO, потолок
`DHT_NEGATIVE_CAP` = 4 096 имён): повторные разрешения того же
имени в пределах TTL **подавляются** (считаются, никогда
повторно не пуллятся). Сканер — или горячее имя, чей владелец
никогда не публиковал, — больше не может усилить один DNS-запрос
в `GetRecord` на каждого пира сети на каждый запрос.
Отрицательная запись умирает по TTL, при прибытии записи
(успешный пулл пишет в настоящий кэш) или будучи вытесненной
из FIFO-потолка.

Открытые счётчики (`scone_dht_negative_hits_total`,
`_expired_total`, `_capped_total` — см. «Метрики» в
`relay.md`).

## TCP (M7b, RFC 7766)

Тот же порт, что UDP (вторая TCP-привязка на адресе `--dns`).
Транспорт следует RFC 1035 §4.2.2: каждое сообщение
префиксовано своей длиной на **2 байта** big-endian.

- **Запрос**: длина префикса ≥ 1 и ≤ 512 байт (DNS-запрос
  помещается в классическую нагрузку — RFC 7766 §6; EDNS не
  обслуживается). Вне границ → немедленное закрытие соединения.
- **Ответ**: бюджет 65 535 байт (максимум 2-байтового префикса)
  — набор, слишком большой для UDP, отдаётся здесь **целиком**,
  TC=0.
- **Пайплайнинг**: несколько запросов на соединение
  обслуживаются последовательно, по порядку (одна запись =
  один префиксованный ответ).
- **Таймаут чтения**: 5 с на чтение (префикс или тело) —
  молчаливый клиент отключается, его слот освобождается.
- **Одновременные соединения**: максимум 64 (семафор); 65-е
  отклоняется немедленно (соединение закрыто), никогда
  в очередь — неограниченного роста задач или памяти нет.
- Ошибки чтения/записи/таймаута: debug-лог + чистое закрытие.
  **Никогда не паниковать на сетевом вводе.**
- Мусор (непонятный запрос) получает молчание, но не закрывает
  соединение: следующий (валидный) запрос обслуживается.

```text
client                     server
  │ [len u16][query]         │
  │ ─────────────────────►   │ cache → authoritative → fallback
  │ ◄─────────────────────   │ [len u16][response ≤ 64 KiB]
  │ (UDP had answered TC=1 → the client retries here)
```

## Границы и ограждения

| Ограждение | Значение |
|---|---|
| UDP-датаграмма (запрос/ответ) | 4096 байт (свыше отклоняется) |
| UDP-бюджет ответа (свыше TC=1) | 512 байт (без EDNS) |
| Максимум TCP-запрос | 512 байт (свыше — закрытие) |
| Максимум TCP-ответ | 65 535 байт |
| Одновременные TCP-соединения | 64 (семафор, немедленный отказ) |
| TCP-таймаут чтения | 5 с |
| Кэш | ГЛОБАЛЬНЫЕ границы 100 000 записей / 64 МиБ по умолчанию, разделены на 16 сегментов (`--dns-cache-limit` / `--dns-cache-max-mem`) |
| Авторитетный TTL | **на запись** (`record.ttl`, границы 1..=2 592 000 с; историческая константа 60 с остаётся только для сервисных ответов) |
| TTL фолбэка (ограничение) | 600 с |
| Параллельные UDP-запросы | 4 096 (`MAX_INFLIGHT_UDP`, семафор; свыше: отброс, клиент повторяет) — настраивается `--dns-max-inflight` (мин 1) |
| Отрицательный кэш DHT | 30 с (`DHT_NEGATIVE_TTL_SECS`), FIFO-потолок 4 096 имён |
| Таймаут на upstream | 2 с |

Соблюдены правила проекта: никогда не паниковать на сетевых
данных; строгое декодирование везде; сервер не касается ни
цепочки, ни хранилища, ни DHT (реле остаётся единственным
авторитетом верификации).

## Тесты

- Юнит (`scone-network::dns`): строгий кодек (QR, сжатие,
  отказы меток), авторитетные ответы, NODATA, NXDOMAIN, REFUSED
  без upstream, фолбэк к UDP-моку, ограниченный кэш, TXT-
  фрагментация, разбор upstream; фикс M6: честность бита AA
  (авторитетное против фолбэка против ошибок, включая
  попадания кэша), усечение TC=1 негабаритного набора, отказ
  от ответа upstream (несовпадение TXID или вопроса), никакого
  кэширования SERVFAIL/REFUSED; сегментированный кэш:
  разброс сегментов, разделённые глобальные границы, 4
  одновременных воркера на горячем имени; горячий путь:
  поиск без аллокаций, упакованные записи, сжатие владельца.
- M7b: бюджет по транспорту (UDP 512 байт → TC=1, TCP → полный
  набор), усечение попадания кэша, настоящий `run_tcp` (набор
  > 512 отдаётся целиком, пайплайнинг 2 запросов, негабаритный
  запрос → закрытие, молчаливый клиент → таймаут 5 с, мусор
  затем валидный запрос на том же соединении), ответ upstream
  > 512 перекодируется TC=1 по UDP / байт в байт по TCP.
- Реальная интеграция (`tests/dns_server.rs`): полное реле
  (включая продакшен devnet) + регистрация + UpdateDomain +
  PutRecord, затем настоящие UDP-запросы: проверенный A (бит
  AA), TXT, NODATA AAAA, NXDOMAIN, фолбэк через мок, повторный
  запрос, подимя через апекс.
- Бинарный E2E (`crates/scone/tests/dns_cli.rs`): настоящий
  бинарник `scone` — `relay --dns`, `identity generate`,
  `domain register`, `domain update --file`, затем `dig`
  (dnsutils) (проверенный A, TXT, NXDOMAIN, REFUSED) на
  настоящем UDP-порту.

## Открытые решения

- Без EDNS (UDP-бюджет остаётся 512 байт; усечение TC=1 + TCP
  покрывает потребность devnet).
- Набор записей не несёт имени на запись: весь набор обслуживает
  каждое подимя апекса (неявный дикий знак). Адресация по записи
  потребовала бы расширения `DnsRecord` (протокол).
- Фолбэк перенаправляет «сырой» запрос: вредоносный upstream
  может ответить что угодно (непроверенный ответ — это
  стандартная рекурсивная модель; имена Scone НИКОГДА через неё
  не проходят).

## GeoDNS (географическая маршрутизация)

> Нормативная спецификация. Любое расхождение документации
> с кодом = баг.

### Встроенная таблица GeoIP (автоматически)

Каждый бинарник встраивает **таблицу соответствия IP → страна**,
скомпилированную в реле: **никакой конфигурации не нужно**,
географическая маршрутизация активна везде, автоматически.

- **Источник данных**: **DB-IP Lite** («IP to Country Lite»),
  лицензия **CC BY 4.0** — допускает распространение с указанием
  авторства: `https://db-ip.com` (курируется ежемесячно; ранее:
  делегирования RIR через `scripts/gen-geo-table.py`, удалены).
  Квантованные ячейки **/20 v4 и /24 v6** (нативная гранулярность
  DB-IP, ~1,3 млн диапазонов, превышает границу памяти парсера) —
  ~96 500 правил. Дата генерации — в заголовке таблицы
  (`assets/embedded-geo.table`).
- **Контрольная сумма**: SHA-256 таблицы вычисляется при
  компиляции (`build.rs`), **перепроверяется при загрузке**
  (несовпадение = типизированный отказ — изменённый бинарник
  никогда не обслуживает географические ответы) и логируется
  при загрузке вместе с указанием авторства. Хеш гарантирует,
  что «все узлы одной сборки разделяют одну таблицу» — это
  ПРОВЕРЯЕМО, а не предполагается.
- **Регенерация**: `scripts/geo-convert.py` (скачивает CSV
  DB-IP Lite текущего месяца, конвертирует — числовая страна,
  континент производный ISO→M49, ASN/регион отсутствуют в Lite).
- **Гранулярность**: страна (числовой ISO 3166-1) + континент
  (UN M49) производный. Ни ASN, ни региона (отсутствуют в Lite —
  потребность ASN/региона ждёт эволюции встроенного пайплайна,
  а не локальной таблицы).
- **Производительность**: поиск **бинарным поиском** по
  отсортированным диапазонам (индекс строится один раз при
  первом использовании, на семейство v4/v6) — измерено ~95
  нс/поиск горячий, ~50 мкс случайный доступ по полной таблице
  (бенчмарк: `cargo test -p scone-network --release --test
  geo_bench -- --ignored`).
- **Самолокация реле**: маршрутизация следует **исходному IP
  каждого запроса** — реле в локальной сети маршрутизирует
  своих локальных клиентов в нужную зону автоматически.
- **Таблица НАВЯЗАНА** (remove-geo-operator-table, 2026-10-22):
  встроенная таблица — **единственный источник** — ни импорта,
  ни переопределения оператором не существует. **Никакой гео-опции
  времени выполнения не существует**: любой флаг `--geo-*` — жёсткий
  отказ clap (геозона навязывается сборкой). Оператор с особыми
  потребностями (ASN, регион) ждёт эволюции встроенного пайплайна,
  а не локальной таблицы.

### Обзор

Домен может публиковать правила **географической
маршрутизации** в своём подписанном наборе записей: записи
`GEOROUTE` (приватный тип Scone `32 768`, вне диапазона IANA).
Резолвер отвечает на вопросы A/AAAA для этих доменов **адресом
конечной точки, выбранной правилом** (область, ближайшая
к позиции КЛИЕНТА, выведенной из его исходного IP через
таблицу), вместо статической записи A/AAAA. Всё остальное
(домены без GEOROUTE, прочие qtype) следует классическим путём
DNS, **байт в байт**.

### Метрики GeoDNS

Точка Prometheus exposed разбивку гео-ответов:

- `scone_dns_geo_answers_total` — всего обслужено GEOROUTE-
  ответов;
- `scone_dns_geo_by_continent_total{continent="<M49>"}` — по
  континентам;
- `scone_dns_geo_by_country_total{country="<ISO>"}` — по
  странам (ограничено самими стандартами: ≤ 9 континентов,
  ≤ 250 стран).

### Запись GEOROUTE (wire)

GEOROUTE = **область** + ≤ 32 **конечных точек** (каноническая
сортировка при декодировании: приоритет по возрастанию, вес по
убыванию, адрес по возрастанию; дубликат = отказ):

```text
GeoScope   = 0x00 (world)
           | 0x01 continent.v (UN M49 code: AF=2, AS=142, EU=150,
                                NA=3, SA=5, OC=9, AN=999)
           | 0x02 country.v   (ISO 3166-1 numeric code: US=840,
                                TW=158, FR=250…)
           | 0x03 region.v    (OPAQUE ISO 3166-2 subdivision, u32:
                                publisher-defined number, compared
                                as is — no local table)
           | 0x04 asn.v       (AS number, u32)
           | 0x05 prefix.addr[16] || prefix.len u8
             (normalized 16-byte IP prefix: IPv4 = address in the
              first 4 bytes + ZERO tail, len ≤ 32;
              IPv6 = 16 free bytes, len ≤ 128; host bits ALWAYS
              zero — a non-normalized prefix is rejected)
GeoTarget  = 0x00 octets[4]  (binary IPv4 address)
           | 0x01 octets[16] (binary IPv6 address)
GeoEndpoint = target || priority.v || weight.v
GEOROUTE    = scope || count.v(≤32) || endpoints…
```

Границы валидации (декодирование): `priority > 0`,
`weight ≤ 100` (`weight = 0` = неактивная конечная точка,
никогда не избирается), TTL в пределах 1..=2 592 000 с, как у
любой записи. Страна/континент, неизвестные локальным таблицам,
**разрешены** на wire: маршрутизация просто откатывается к более
высокой области.

**Обратная совместимость wire (v1 → v2)**: байты v1 НЕИЗМЕННЫ —
области v1 (мир/континент/страна) сохраняют свои дискриминанты
`0x00..=0x02` и точное кодирование; три новые области берут
следующие дискриминанты (`0x03..=0x05`) в полном порядке,
согласованном с канонической сортировкой
(`World < Continent < Country < Region < Asn < IpPrefix`).
Декодер v1, встретив дискриминант ≥ `0x03`, уже строго
проваливался (запись отклонялась); байты, произведённые v1,
декодируются идентично (см. замороженный тест `geo_known_bytes`).

### Выбор (разрешение)

1. **Область** — убывающая специфичность, **6 уровней**:
   **самый длинный совпадающий IP-префикс → точный AS → точная
   страна → точный регион → континент → мир**.
   - *IpPrefix*: среди маршрутов, чей префикс совпадает с IP
     клиента (как известно локатору: `client_ip`, иначе
     известные префиксы происхождения), побеждает **самый
     длинный** (`len` макс); при равном `len` — первый
     в каноническом порядке (порядок слайса `routes`,
     отсортированного при кодировании). Подразделение менее
     специфично, чем префикс/AS (которые идентифицируют точную
     сеть) и менее, чем страна (непрозрачная нумерация,
     надёжна, только если публикатор и локатор разделяют одну
     и ту же), но более, чем континент (он содержится в своей
     стране, тем более в своём континенте).
   - *Asn*: точный номер AS клиента.
   - *Country*: точная страна.
   - *Region*: точное подразделение (непрозрачный
     идентификатор).
   - *Continent*: предоставляется локатором **или выводится
     из страны** через локальную таблицу
     (`continent_of_country`); страна, неизвестная таблице,
     откатывается к явному континенту или миру.
   - *World*.
   [`GeoLocation`] v1 (region/asn/prefixes/client_ip не
   установлены) производит ровно поведение v1: страна →
   континент → мир. Ни одного совпадающего маршрута (включая
   без области World) → классическое поведение DNS, как будто
   GEOROUTE не существует.
2. **Приоритет** — семантика в стиле SRV: избирательно только
   группа **минимального приоритета**; высшие приоритеты —
   уровни **фолбэка**.
3. **Вес** — внутри избранной группы, **детерминированная
   взвешенная** жеребьёвка: стабильный хеш (SplitMix64) нонса
   (счётчик запросов резолвера) против кумулятивных весов. Без
   RNG: два запроса с одним нонсом дают один результат,
   возрастающие нонсы распределяют пропорционально весам.
   `weight = 0` = неактивна, никогда не избирается (даже одна —
   переход на следующий уровень).
4. **Подписанный порядок, ноль проверок** — резолвер НИКОГДА не
   судит о доступности конечной точки: каждая активная конечная
   точка (weight > 0) избранной области — кандидат, голова
   минимального уровня избирается взвешенной жеребьёвкой, а
   следующие служат фолбэком **в подписанном порядке набора
   записей** (порядок и ЕСТЬ механизм фолбэка). Достижимость
   конечной точки — забота её оператора, никогда резолвера.

### Ответ

- Один адрес: **A если IPv4, AAAA если IPv6** — строгая
  фильтрация по семейству согласно qtype (вопрос A НИКОГДА не
  отвечает IPv6, и наоборот).
- TTL = TTL исходной записи GEOROUTE (ограничен при
  декодировании общими правилами TTL).
- AA установлен (авторитетный ответ — GEOROUTE является
  проверенной подписанной записью, как любая другая).
- Пустой ответ после фильтрации (нет кандидата нужного
  семейства, нет маршрута для зоны) →
  резолвер продолжает по классическому пути (обычно NODATA:
  NOERROR, 0 ответов); rcodes ошибок следуют общим правилам
  (никогда не кэшируются).
- Классическая запись A/AAAA, сосуществующая в наборе, имеет
  ПРИОРИТЕТ над гео (гео применяется только при отсутствии
  wire-ответа для qtype).

### Кэш: явное решение

Решение гео-маршрутизации **НИКОГДА не кэшируется** под
`(qname, qtype)`: оно зависит от области клиента резолвера,
и такой ключ отдавал бы маршрут US клиенту из TW. Гео-ответы
перевычисляются на каждый запрос (стоимость: один select_scope
+ взвешенная жеребьёвка, мкс) и обходят кэш. Классический кэш
(qname, qtype) остаётся неизменным для всего остального —
включая NODATA, произведённый, когда гео ничего не решает.
Rcode ошибок остаются никогда не кэшируемыми.

### NS-делегирование (записи `ns`) — владелец решает, кто обслуживает

Владелец домена выбирает режим обслуживания для каждого домена:

- **DHT (по умолчанию)** — без записи NS сеть Scone обслуживает
  A/AAAA on-chain (реле `--dns` или мост NSD через export);
- **независимые NS** — владелец добавляет записи
  `ns <ip-или-имя>` (ЕГО nameservers, прямой IP или имя): домен
  ДЕЛЕГИРОВАН — сеть прекращает обслуживать его содержимое
  (A/AAAA → NODATA + авторитет NS), и всякий резолвящий следует
  NS владельца. Граница: **12 различных NS на домен** (все формы,
  дедуплицированные по значению — зеркало реальных лимитов
  реестров). Удаление NS освобождает слот; удаление всех
  восстанавливает режим DHT.

**Никаких проверок здоровья не существует**: доступность конечных
точек — забота их операторов — резолвер обслуживает подписанный
набор записей как есть, в порядке записей (порядок записей и есть
механизм фолбэка).

### Безопасность

- Записи GEOROUTE — подписанные записи, как любые другие:
  проверены против цепочки (владелец, sequence, record_hash)
  до любого использования. **Никакого сетевого доверия без
  валидации** — непроверенный DHT GEOROUTE никогда не отвечает.
- Позиция клиента приходит из **автоматически обнаруженного
  контура**: реле само локализуется через свой внешний адрес
  (STUN/AutoNAT/UPnP), разрешаемый навязанной сборкой встроенной
  таблицей — LAN-клиенты (приватный исходный IP) наследуют эту
  позицию, интернет-клиенты разрешаются по их собственному IP,
  неизвестное откатывается к World. Никогда из сетевого GeoIP-API
  (никакой утечки запросов, никаких зависимостей) и никогда из
  заявления оператора (зоны навязываются сборкой).
- Жеребьёвка детерминирована и локальна: никакого секрета,
  никакой непредсказуемости не требуется (безопасность —
  безопасность подписи записи, не жеребьёвки).

### Полный пример (референс-спецификация)

`www.example.scone` публикует (апекс `example.scone`, весь
набор обслуживает каждое подимя):

| Область | Конечная точка | Приоритет | Вес |
|---|---|---|---|
| US (840) | 10.1.0.1 | 10 | 70 |
| US (840) | 10.1.0.2 | 10 | 30 |
| US (840) | 10.2.0.1 | 20 | 100 |
| TW (158) | 10.3.0.1 | 10 | 80 |
| TW (158) | 10.4.0.1 | 10 | 20 |
| TW (158) | 10.2.0.1 | 20 | 100 |
| WORLD | 10.0.0.1 | 100 | 100 |

Ожидаемое поведение:

- клиент **US** → 10.1.0.1 (≈70%) или 10.1.0.2 (≈30%); уровень
  p20 достигается только если ни одна конечная точка p10 не
  активна (weight = 0 везде) → тогда **10.2.0.1**;
- клиент **TW** → 10.3.0.1 (≈80%) или 10.4.0.1 (≈20%);
- клиент **FR** (250) → нет маршрута FR или EU в наборе →
  WORLD → **10.0.0.1**;
- вопрос **A** на маршруте только-IPv6 → пустой ответ (никогда
  IPv6 в A);
- домен без применимого правила → тот же вопрос, классическое
  поведение (NODATA: GEOROUTE не имеет wire rdata A).

### Опции CLI (`scone relay`)

| Опция | По умолчанию | Роль |
|---|---|---|
| (ничего — GeoDNS всегда включён, гео навязано сборкой) | вкл | Автоматическая маршрутизация: реле обнаруживает свою позицию (STUN → встроенная таблица), LAN-клиенты наследуют, интернет-клиенты по своему IP |
| `--geo-ip-table`, `--geo-config`, `--geo-country/…`, `--health-*` | — | (УДАЛЕНЫ — жёсткий слом: геозона навязывается сборкой, и резолвер не выполняет никаких проверок здоровья; ни одного флага времени выполнения не существует) |

#### Встроенная таблица — единственный источник

Таблица GeoIP **навязана сборкой** (DB-IP Lite, квантованная —
см. раздел о встроенной таблице выше): ни одну таблицу оператора
импортировать нельзя. Разрешение: **исходный IP DNS-запроса**
(на клиента: UDP `recv_from` / TCP `peer_addr`) сравнивается
в 16 байтах со встроенной таблицей; побеждает правило с **самым
длинным совпадающим префиксом** (при ничьей — первое в порядке
файла).

- **приватный/немаршрутизируемый источник** (RFC1918, ULA
  fc00::/7, link-local, loopback): клиент ВНУТРИ сети реле —
  он наследует собственную обнаруженную позицию реле;
- **публичный источник, отсутствующий в таблице**: World (никакого
  гео-дробления — никогда неверного ответа).

**Строгость** сохраняется для любой будущей поверхности таблицы:
некорректная строка — типизированная ошибка старта, несущая номер
провинившейся строки; никогда молча игнорируемая строка, никогда
частичная таблица.

#### Приоритеты опций

- **Локатор**: встроенная таблица НАВЯЗЫВАЕТ геолокацию — никакого
  переопределения оператором. Реле обнаруживает свою позицию через
  свой внешний адрес (STUN/AutoNAT/UPnP, разрешаемые таблицей);
  LAN-клиенты наследуют эту позицию, интернет-клиенты разрешаются
  по их исходному IP, неизвестное откатывается к World.

Пример (гео-маршрутизация активна БЕЗ каких-либо гео-флагов):

```bash
scone relay --dns 127.0.0.1:5353
```


## DoH / DoT (шифрованные транспорты) — через внешний фронтенд

DNS-сервер Scone говорит **чистыми UDP и TCP** (RFC 1035 /
7766) — это нативный объём, полный и протестированный. Шифрованные
транспорты к *конечному клиенту* (DoH — DNS-over-HTTPS,
RFC 8484; DoT — DNS-over-TLS, RFC 7858) **делегированы
стандартному фронтенду**: Scone отдаёт данные, фронтенд
обслуживает транспорт.

Почему такой дизайн: нативный DoH-сервер потребовал бы полного
HTTPS-стека внутри узла (сертификаты, обновление, HTTP/2) —
большая эксплуатационная поверхность нулевой пользы до
появления конечных пользователей на стороне браузера.
Существующие фронтенды делают это лучше и дольше; узел
остаётся минимальным.

### Пример: unbound, делающий DoH перед реле Scone

`/etc/unbound/unbound.conf`:

```
server:
    interface: 127.0.0.1
    port: 5354
    do-ip4: yes
    do-udp: no
    do-tcp: yes

    # DoH (RFC 8484) on 443
    https-port: 443
    tls-service-key: "/etc/unbound/scone.key"
    tls-service-pem: "/etc/unbound/scone.pem"

forward-zone:
    name: "."
    forward-addr: 127.0.0.1@5353   # the Scone relay (--dns 127.0.0.1:5353)
```

Сертификат (`scone.pem`/`scone.key`) получается как для любого
TLS-сервиса — например, certbot/acme.sh на домене резолвера.
Клиенты DoH затем указывают на `https://dns.example.tld/dns-query`.

### Пример: knot-resolver, делающий DoT

`/etc/knot-resolver/kresd.conf`:

```
net.listen('127.0.0.1', 5353, { kind = 'dns' })
net.listen('0.0.0.0', 853, { kind = 'tls' })
tls.cert_file = '/etc/knot-resolver/scone.pem'
tls.key_file  = '/etc/knot-resolver/scone.key'
```

### Что добавляет фронтенд

- **Шифрование канала клиент→фронтенд** (враждебный сегмент:
  сеть пользователя); сегмент фронтенд→реле остаётся локальным
  (та же машина или доверенная сеть).
- **Дополнительный кэш на стороне фронтенда** (кэш unbound/knot
  тоже — безвреден, TTL Scone остаётся верхней границей).
- **Стабильную точку входа** (IPv4/IPv6, домен), пока реле
  перемещаются.

### Чего фронтенд НЕ делает

- Он ничего не *верифицирует*: каждый ответ реле уже проверен
  против цепочки до кэширования (см. «Путь разрешения»).
  Фронтенд перенаправляет уже авторитетные ответы.
- Он не заменяет децентрализацию: DoH-фронтенд —
  *эксплуатируемый* сервис — выбор оператора резолвера,
  а не протокола. Каждое реле Scone остаётся независимо
  используемым по нативным UDP/TCP.

### Будущая нативная реализация (задокументировано, не
обязательство)

Нативный DoH-транспорт (`--doh ADDR`) остаётся мыслимым:
поскольку wire-формат идентичен (RFC 8484 переиспользует
бинарные DNS-сообщения), это был бы POST/GET-декод + HTTP/2
за TLS-прокси (caddy/nginx с сертификатами), сам узел остаётся
без TLS. Работ не ведётся — спрос придёт с конечными
пользователями.
