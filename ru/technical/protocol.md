# Протокол

Референс-документ протокола Scone: бинарный формат, каноническое
кодирование, транзакции, DNS-записи, блоки, P2P-сообщения,
ограничения и совместимость версий. Референсная реализация — крейт
[`scone-protocol`](https://github.com/sconenet/scone/tree/main/crates/scone-protocol).

Пункты, помеченные **(предварительно)**, не являются окончательными.

## Версия протокола

- константа: `PROTOCOL_VERSION: u32 = 1` (`scone-protocol`);
- переносится в `Hello.version` (рукопожатие) и `BlockHeader.version`;
- правила совместимости:
  - полученная версия **выше** локальной → отклонить
    (`ProtocolError::UnsupportedVersion`); узел не угадывает формат
    версии, которую не знает;
  - версия `0` → недопустима;
  - существует только один набор форматов: байты версии транзакции
    (`0x01`) и версии блока должны совпадать с локальными
    значениями **точно**;
- на этом этапе нет разделения major/minor: одно целое число,
  увеличиваемое при любом ломающем изменении формата передачи.

## Принципы бинарного формата

- бинарный, никогда JSON для данных протокола;
- детерминированный и канонический: два логически равных объекта
  производят **ровно те же байты**;
- последовательный разбор, без аллокаций где возможно (заимствование
  байт);
- весь сетевой ввод недоверенный: длины и счётчики проверяются
  **до** любой аллокации; декодирование никогда не паникует.

### Порядок байтов

- все целые — варинты LEB128 (7-битные группы, младшие значащие
  первыми): нативный порядок байтов неприменим;
- адреса IPv4/IPv6 и 32-байтовые идентификаторы: «сырые» байтовые
  массивы, без префикса длины;
- в формате нет фиксированного широкого целого: единое правило
  кодирования целых.

### Варинт (минимальный LEB128)

Каждый байт несёт 7 бит данных; старший бит равен 1 у каждого
байта, кроме последнего. `u64` помещается в 1–10 байт.

| значение | байты (hex) |
|---|---|
| 0 | `00` |
| 1 | `01` |
| 127 | `7f` |
| 128 | `80 01` |
| 255 | `ff 01` |
| 16 384 | `80 80 01` |
| 2^32 | `80 80 80 80 10` |
| u64::MAX | `ff ff ff ff ff ff ff ff ff 01` |

Кодирование должно быть **минимальным**: раздутые формы
отклоняются при декодировании (`InvalidVarint`). Это необходимое
условие того, чтобы значение имело только одну валидную
последовательность байт (каноническое кодирование). Отклонения:
`80 00` (неминимально), `ff×9 02` (переполнение u64), `ff×10`
(слишком длинно).

### Строки и байты

- `bytes`: варинт-длина + «сырые» байты;
- `str`: то же, с обязательным декодированием UTF-8;
- каждая длина ограничена (см. [Ограничения](#ограничения)) и
  проверяется перед чтением.

### Идентификаторы

| Тип | Представление в wire |
|---|---|
| `DomainId` | 32 «сырых» байта |
| `TldId` | 32 «сырых» байта |
| `OwnerId` | 32 «сырых» байта |
| `PublicKeyRef` | 32 «сырых» байта |
| `RecordHash` | 32 «сырых» байта |
| `BlockHash` | 32 «сырых» байта |
| `MerkleRoot` | 32 «сырых» байта |
| `DomainName` | `str` (≤ 253 байт, ревалидируется `scone-core`) |

Вычисления (`BLAKE3-256` + префиксы `SCONE-DOMAIN-V1` и т. д.)
остаются определёнными в `scone-core` (см.
`/docs/en/general/naming.md`).

## Транзакции

```text
Transaction = disc u8 || version u8 || payload
```

| Дискриминант | Тип |
|---|---|
| `0x21` | `RegisterDomain` |
| `0x2A` | `RegisterTldPow` |
| `0x52` | `UpdateDomain` |
| `0x57` | `RenewTldPow` |
| `0x84` | `RegisterDomainPow` |
| `0x93` | `RegisterTld` |
| `0xC3` | `RenewDomainPow` |

Каждый дискриминант — произвольная непрозрачная константа (без
логической последовательности; `0x00` никогда не валиден) — полная
нормативная таблица в `/docs/en/technical/transactions.md`.

Байт `version` (текущее значение `0x01`) следует за
дискриминантом: любое другое значение явно отклоняется
(`UnsupportedVersion(value)`). Большинство транзакций подписаны
(Ed25519) — ИСКЛЮЧАЯ четыре формы pow-to-owner без подписи
(`0x2A`, `0x57`, `0x84`, `0xC3`): замайненное доказательство и
ЕСТЬ авторизация, а его challenge привязывает ключ бенефициара и
сеть. Полная спецификация, подписываемая полезная нагрузка
и правила валидации — в **`/docs/en/technical/transactions.md`**
(нормативно).

С изменения wire от 2026-09 **транзакции больше не несут поле
`network`**: `network_id` (`str` ≤ 16) вводится в
**подписываемую полезную нагрузку** (подписанные формы) или
**PoW-challenge** (формы pow-to-owner) — tx, сделанная для одной
сети, никогда не переносится в другую (см.
`/docs/en/technical/blockchain.md`).

### REGISTER_DOMAIN (0x21)

```text
name(str ≤ 253) domain_id[32] owner[32] timestamp.v proof(bytes ≤ 256) public_key[32] signature[64]
```

`RegisterDomain` несёт **каноническое имя открытым текстом**,
за которым следует его `DomainId` — согласованность
`domain_id == DomainId(name)` перепроверяется при декодировании
(перевычисляется, никогда не доверяется). `proof` несёт PoW
регистрации (20 байт: nonce + эпоха + сложность — «соль» эпохи
`epoch = height/144` применяемого блока, проверяется СТРОГО при
применении против сетевой константы и эпохи блока; типизированный
отказ `ProofEpochMismatch` при несоответствии — M8b, см.
`transactions.md`). `public_key` — ключ Ed25519 подписанта (ровно
32 байта); `owner` должен быть выведением BLAKE3 этого ключа
(перевычисляется, никогда не доверяется); `signature` — ровно
64 байта.

### REGISTER_TLD (0x93)

```text
tld(str ≤ 63) tld_id[32] owner[32] timestamp.v proof(bytes ≤ 256) public_key[32] signature[64]
```

Заявка на TLD (реестр, отдельный от реестра доменов, M7): TLD
**несётся открытым текстом**, как имя домена (M8b — задача PoW
выводится из имени), а `tld_id` — это выведение `SCONE-TLD-V1`
этого имени, не пересекающееся ни с одним `DomainId` по
построению. Правила состояния (M8b): TLD свободен + не
зарезервирован ICANN (`IcannTldReserved` — корневые TLD ICANN
недоступны для заявки никем) + PoW со сложностью **по длине**
метки (кривая `pow_length` — см. `blockchain.md`); заявленный —
закрыт (только назначение).

### UPDATE_DOMAIN (0x52)

```text
domain_id[32] owner[32] sequence.v record_hash[32] public_key[32] signature[64]
```

Инвариант перепроверяется при декодировании: `sequence > 0` и
`owner` == выведение из `public_key`. Без `timestamp`:
упорядочивание идёт через `sequence`. Транзакция несёт только
компактные ссылки — полное DNS-содержимое остаётся в DHT
(см. ниже).

## DNS-записи (сторона DHT)

Полные DNS-записи никогда не попадают в блокчейн: они
обмениваются через DHT (сообщения `GetRecord`/`Record`) и
фиксируются в цепочке только своим `RecordHash`.

### RecordData

```text
RecordData = type.v || ttl.v || payload(type)
```

Коды типов — **настоящие DNS-коды** (IANA). TTL (секунды,
варинт) следует за кодом типа и покрывает всю запись: границы
`MIN_TTL = 1` .. `MAX_TTL = 2 592 000` (30 дней; по умолчанию
`DEFAULT_TTL = 86 400`).

| Код | Тип | Полезная нагрузка |
|---|---|---|
| 1 | A | 4 байта |
| 2 | NS | `name` |
| 5 | CNAME | `name` |
| 12 | PTR | `name` |
| 15 | MX | `preference.v`, `name` |
| 16 | TXT | `str` ≤ 4096 |
| 28 | AAAA | 16 байт |
| 33 | SRV | `priority.v`, `weight.v`, `port.v`, `target(name)` |
| 257 | CAA | `flags u8`, `tag` (1–15 Б), `value` (`str` ≤ 4096) |
| 32768 | GEOROUTE | GeoRoute (см. ниже) |
| другое | Unknown | code.v + `bytes` ≤ 4096 |

Пример: `A 192.0.2.1` (TTL 86 400) → `01 80 a3 05 c0 00 02 01`
(тип, TTL-варинт, адрес).

`Unknown` с известным кодом отклоняется при кодировании (при
декодировании такой возникнуть не может).

#### GEOROUTE (GeoDNS)

Приватный тип Scone (не-IANA-диапазон). Одно правило
географической маршрутизации:

```text
GeoRoute  = scope || count.v(≤ 32) || endpoint…
scope     = 0x00                    -- world
          | 0x01 continent.v        -- UN M49
          | 0x02 country.v          -- ISO 3166-1 numeric
          | 0x03 region.v           -- region code
          | 0x04 asn.v              -- AS number
          | 0x05 prefix.addr[16] || prefix.len u8   -- IP prefix (normalized)
endpoint  = target || priority.v || weight.v
target    = 0x00 octets[4]          -- binary IPv4
          | 0x01 octets[16]         -- binary IPv6
```

**Каноническое правило**: конечные точки одной области
кодируются **отсортированными** (приоритет по возрастанию, затем
вес по убыванию, затем адрес по возрастанию); сортировка
применяется при кодировании, а неотсортированный wire
отклоняется при декодировании (`NonCanonical`), как и для
наборов записей. Полные дубликаты конечных точек отклоняются.

**Валидация**: `priority > 0`, `weight ≤ 100` (0 = неактивная
конечная точка), ≤ 32 конечных точек на область
(`GEO_MAX_ENDPOINTS`). Код страны/континента, неизвестный
локальной таблице (`continent_of_country`), **принимается** на
уровне wire: таблица резолвера может быть более свежей, чем
у публикатора. TTL — тот же, что у родительского `RecordData`
(без изменений).

### DnsRecord

```text
domain_id[32] sequence.v expiration.v count.v(≤ 256) records…
```

**Каноническое правило**: набор записей — неупорядоченная
коллекция. Он кодируется **отсортированным по лексикографическому
порядку индивидуального кодирования каждой записи**, строго
по возрастанию (дубликаты отклоняются). Неотсортированный wire
отклоняется при декодировании (`NonCanonical`). Порядок исходного
`Vec` не переносится.

### SignedDnsRecord

```text
DnsRecord owner[32] signature(bytes ≤ 128)
```

### RecordHash

```text
RecordHash = BLAKE3-256("SCONE-RECORD-V1" || canonical(DnsRecord))
```

Хеш покрывает **только содержимое записи**; подпись владельца
проверяется отдельно по тем же каноническим байтам. *(Решение:
обязательство не покрывает подпись — более ранняя версия этого
документа упоминала «полный SignedDnsRecord»; привязка хеша
к подписи ничего не давала и привязывала обязательательство
к схеме подписи.)*

## Блоки

### BlockHeader

```text
version.v height.v prev_hash[32] tx_root[32] timestamp.v consensus(bytes ≤ 65,536)
```

- `version`: версия протокола (правила выше);
- `height`: высота (генезис = 0);
- `prev_hash`: хеш предыдущего блока (нули для генезисного
  блока);
- `tx_root`: обязательательство по списку транзакций (дерево
  Меркла, определённое `scone-blockchain`, см.
  `/docs/en/technical/blockchain.md`);
- `timestamp`: информация упорядочивания (Unix, секунды);
- `consensus`: полезная нагрузка продюсера (`SCONE-BLOCK-V1 ‖
  pk[32] ‖ sig[64]`, см. `blockchain.md`) — генезис сети несёт
  «сырой» `network_id`, а генезис распределений (mainnet
  kickstarter) может нести манифест `ALLOC-V1` (≤ 60 КиБ);
  ограничен `MAX_CONSENSUS_LEN` (64 КиБ).

### Block

```text
BlockHeader tx_count.v(≤ 4096) transactions…
```

Последовательный разбор; счётчик ограничен **до** аллокации;
любое усечение отклоняется. В отличие от наборов записей,
порядок транзакций **значим** (порядок консенсуса) и сохраняется
точно.

`BlockHash` (хеш канонического заголовка) и `tx_root`
вычисляются `scone-blockchain` по кодированиям, определённым
здесь (точные формулы в `/docs/en/technical/blockchain.md`).

## P2P-сообщения

```text
Message = disc u8 || payload
```

Транспорт (фрейминг, libp2p…) вне области; кадр транспорта не
должен превышать `MAX_MESSAGE_LEN` (1 МиБ).

| Disc | Сообщение | Направление | Полезная нагрузка | Лимит | Ожидаемый ответ |
|---|---|---|---|---|---|
| `0x01` | `Hello` | оба | `version.v` | — | `Hello` |
| `0x02` | `Ping` | оба | — | — | `Pong` |
| `0x03` | `Pong` | оба | — | — | — |
| `0x04` | `GetBlock` | оба | `hash[32]` | — | `Block` |
| `0x05` | `GetBlocks` | оба | `start.v` `max.v` | `max ≤ 128` | ≤ `max` × `Block` |
| `0x06` | `Block` | оба | `Block` | tx ≤ 4096 | — |
| `0x07` | `Transaction` | оба | `Transaction` | — | — |
| `0x08` | `GetRecord` | оба | `domain_id[32]` | — | `Record` |
| `0x09` | `Record` | оба | `SignedDnsRecord` | — | — |
| `0x0a` | `Checkpoint` | оба | `Checkpoint` | подписанты ≤ 64 | — |
| `0x0b` | `GetCheckpoints` | оба | — | — | окно чекпоинтов |
| `0x0c` | `GetStatus` | оба | — | — | `NodeStatus` |
| `0x0d` | `NodeStatus` | оба | состояние узла (сеть, тип, высота, NAT, домены, мемпул, пиры, финальность, свежие операторы) | — | — |
| `0x0e` | `LookupName` | оба | `name(str)` | — | `NameState` |
| `0x0f` | `NameState` | оба | состояние имени в цепочке + TLD, вкл. CAS-поколение (счётчики мутаций, registered_at) | — | — |
| `0x10` | `GetOwnedNames` | оба | `owner[32]` | — | `OwnedNames` |
| `0x11` | `OwnedNames` | оба | живые домены + TLD владельца | — | — |
| `0x12` | `Error` | ответ | сообщение об ошибке уровня приложения (`str`) | — | — |

### Чекпоинт (M5)

Агрегированный чекпоинт идёт в wire как: тег `SCONE-CKPT-V1` ||
тело `CheckpointData` (116 Б, LE — идентично концу преобразования
подписи: `epoch(8) height(8) block_hash(32) prev_checkpoint_hash(32)
state_root(32) recovery(4)`) || `count.v` || `pk[32] ‖ sig[64]` на
подписанта, **отсортированных по возрастанию pk, без
дубликатов**, `count ≤ 64` (`MAX_CHECKPOINT_SIGNERS`). Строгое
декодирование: усечение, неверный тег, неканонический pk,
дубликаты или отсутствие сортировки = отказ (`None`), никогда
паника (порча протестирована фаззингом).

`GetCheckpoints` запрашивает окно финальности; ответ — окно
`checkpoint_window()` (не более `CHECKPOINT_KEEP` чекпоинтов, от
старых к новым) одним или несколькими сообщениями `Checkpoint`.

`TxId` теперь определён `scone-blockchain`
(`BLAKE3-256("SCONE-TX-V1" || canonical(Transaction))`, см.
`/docs/en/technical/blockchain.md`). Мемпул и оконный анти-replay
(`TxReplay`, `REPLAY_WINDOW_BLOCKS = 256`) поставляются в реле
(M4); отложен только `GetTransaction` (его определение зависит
от оставшихся решений по консенсусу).

## Разделение блокчейн / DHT

```text
BLOCKCHAIN                      DHT
──────────                      ───
domain_id                       domain_id
owner                           SignedDnsRecord (full, signed)
sequence
record_hash
```

Цепочка говорит, *кто* владеет и *каково текущее состояние*
(sequence + record_hash). DHT предоставляет *содержимое*. Запись
DHT принимается тогда и только тогда, когда:

1. её подпись валидна для владельца, зарегистрированного
   в цепочке;
2. её `sequence` согласован с цепочкой (или выше её);
3. `RecordHash`, перевычисленный по её каноническому
   кодированию, совпадает с `record_hash` цепочки.

## Ограничения

| Константа | Значение | Роль |
|---|---|---|
| `MAX_NAME_LEN` | 253 | длина имени |
| `MAX_TLD_LEN` | 63 | длина TLD |
| `MAX_TXT_LEN` | 4096 | строка TXT |
| `MAX_PROOF_LEN` | 256 | доказательство регистрации |
| `MAX_SIGNATURE_LEN` | 128 | подпись (Ed25519 = 64) |
| `MAX_RECORDS_PER_SET` | 256 | записей на набор |
| `MAX_DHT_RECORD_LEN` | 64 КиБ | кодированная подписанная DNS-запись (полезная нагрузка DHT: wire, хранилище, gossip) — общая граница проверяется при кодировании И перед любым декодированием; на 15–30× выше любого реалистичного набора (SPF+DKIM+DMARC ≈ 2–5 КиБ), в 16× ниже потолка транспорта. |
| `GEO_MAX_ENDPOINTS` | 32 | конечных точек на область GeoRoute |
| `MAX_UNKNOWN_DATA` | 4096 | данные неизвестного типа |
| `MAX_TXS_PER_BLOCK` | 4096 | транзакций на блок |
| `MAX_CONSENSUS_LEN` | 64 КиБ | полезная нагрузка консенсуса заголовка (расширена для генезис-манифеста `ALLOC-V1` — mainnet kickstarter) |
| `MAX_BLOCKS_PER_REQUEST` | 128 | блоков на `GetBlocks` |
| `MAX_MESSAGE_LEN` | 1 МиБ | кадр транспорта (рекомендуется) |

Любое превышение → `LimitExceeded`, обнаруженное до аллокации:
вредоносный пир не может вызвать непропорциональную аллокацию
при декодировании.

## Каноническое кодирование

Фундаментальное правило:

```text
canonical object → canonical binary encoding → hash / signature
```

- только минимальные варинты;
- наборы записей отсортированы строго по возрастанию;
- у логически равного объекта ровно **одна** валидная
  кодировка;
- декодирование отклоняет неканонические формы (`NonCanonical`),
  поэтому не существует нескольких валидных кодировок одного
  объекта.

## Обработка ошибок

`ProtocolError` (`scone-protocol::error`):

| Вариант | Значение |
|---|---|
| `Truncated` | ввод оборвался посреди значения |
| `InvalidVarint` | неминимальный, переполняющий или слишком длинный варинт |
| `IntegerOutOfRange` | целое не помещается в целевой тип |
| `UnsupportedVersion` | нулевая или выше локальной версия |
| `UnknownDiscriminant` | неизвестный дискриминант транзакции/сообщения |
| `LimitExceeded` | длина или счётчик за пределом |
| `InvalidUtf8` | не-UTF-8 строка |
| `TrailingBytes` | байты остались после полного значения |
| `Validation` | нарушение инварианта `scone-core` |
| `NonCanonical` | валидное по полям, но неканоническое кодирование |

Декодирование никогда не паникует на сетевых данных.

## Подписи

- схема: **Ed25519** (RFC 8032) через `scone-crypto`
  (`ed25519-dalek`, проверка `verify_strict` — маллеабельные
  подписи и слабые ключи отклоняются);
- **транзакции цепочки**: каждая `RegisterDomain` / `RegisterTld`
  / `UpdateDomain` встраивает `public_key` (32 Б) + `signature`
  (64 Б) по полезной нагрузке
  `"SCONE-TX-SIG-V1" || canonical_encode(tx_without_signature)`;
  полная нормативная спецификация:
  `/docs/en/technical/transactions.md`;
- **записи DHT** (`SignedDnsRecord`): подписываемая полезная
  нагрузка — каноническое кодирование `DnsRecord`; проверка
  пересекает `record + owner + signature` с идентичностью,
  зарегистрированной в блокчейне;
- сквозное правило: `owner` и все хеши/обязательства
  **перевычисляются**, никогда не берутся из предоставленного
  значения.

## Правила консенсуса

Поставлено (описано в `/docs/en/technical/blockchain.md`):
подписанный продюсер блока (полезная нагрузка `SCONE-BLOCK-V1`,
комитет, избранный чекпоинтами), финальность агрегированными
чекпоинтами (`SCONE-CKPT-V1`, выбор форки по порогу
финальности), PoW регистрации по длине имени. Оставшиеся темы:
тонкие антиспам-сборы, ротация ключа владельца.
