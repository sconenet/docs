# Хранилище — локальная персистентность узла (redb)

> Нормативный документ. Любое расхождение между этим документом
> и `crates/scone-storage/src/` — баг (определить источник истины,
> исправить). Референс реализации: крейт `scone-storage` (формат
> v1), бэкенд `redb` 4.2.

## Назначение

Встроенная локальная персистентность узла: канонические блоки,
состояния доменов, кэш DHT, метаданные. Хранилище — это
**персистентность**, никогда не авторитет: ОЗУ-состояние
([`ChainState`], источник консенсуса) реконструируется при старте
из хранилища, и каждая запись — **дельта** (домены, изменённые
блоком), а никогда не полная копия состояния.

Сквозное ограничение (для пользователя, на каждой вехе):
**минимальный след памяти**. Большие объёмы (блоки, состояния
доменов, кэш DHT) живут в redb и доступны через курсоры/
диапазоны — никогда полностью не грузятся в ОЗУ, никогда
бесполезно не дублируются.

## Граница: трейт `NodeStore`

`crates/scone-storage/src/lib.rs` определяет единственное лицо
хранилища, видимое остальному коду (блокчейн, будущее реле M4):

- `append_block(height, hash, bytes)` /
  `append_block_with_state(..., deltas)` — атомарное добавление
  (см. ниже);
- `block_at_height(h)` / `block_by_hash(hash)` — точечные чтения;
- `tip() -> (height, hash)` — O(1), читается из `meta`;
- `put_domain_state` / `domain_state` / `domain_count` —
  **поддерживаемый** счётчик (`meta["domain_count"]`), никогда
  `COUNT(*)`;
- `iterate_domains(after, max) -> DomainPage` — курсорная
  пагинация (партии по 100 по умолчанию), восходящий порядок
  байт `DomainId`;
- `put_tld_state` / `tld_state` / `tld_count` / `iterate_tlds` —
  те же контракты для реестра TLD (`tld_count` поддерживаемый,
  ограниченный курсор) (M7d);
- `put_dht_cache` / `dht_cache` — непрозрачные байты
  `SignedDnsRecord`;
- `resolve_name(canonical)` / `resolve_tld(tld)` — персистентный
  индекс Имя→Id (P0.2), точечный поиск O(1), без итерации по
  доменам (по умолчанию `None` = бэкенд без индекса, вызывающий
  откатывается к `iterate_domains` или состоянию цепочки);
- `tld_floors_all` / `snapshot_tld_floors_all` — чтение порогов
  жизни открытых TLD (опция владельца: выделенные таблицы,
  живая `tld_floors_v1` и замороженная `snapshot_v1_floors`);
- `rewind_to_height(h)` — реорг: удаляет блоки выше `h`
  и возвращает `tip`/`tip_height` на `h` в ОДНОЙ транзакции
  (прелюдия к `persist_state_snapshot`, см. ниже);
- `meta_get` / `meta_set`;
- `snapshot_meta` / `snapshot_domains` / `snapshot_tlds` — чтение
  снапшота состояния загрузки (M6b; пустые значения по умолчанию
  = бэкенд без снапшота, `load_chain` тогда откатывается
  к полной загрузке).

Правила:

- **Никаких типов redb в API**: только байты (`&[u8]`, `[u8; 32]`)
  и типы ядра. Бэкенд заменим.
- **Без async, без внутренней мутабельности**: записи берут
  `&mut self` (redb сериализует писателей), чтения берут `&self`
  (одна короткая транзакция чтения на вызов).
- API никогда не ревалидирует блоки: хеш, переданный
  в `append_block*`, — **перевычисленный** хеш, поставленный
  вызывающим (`Blockchain::push_block`).

## Схема таблиц redb

| Таблица | Ключ (сортировка) | Значение |
|---|---|---|
| `blocks_by_height` | высота `u64` (упорядоченное b-tree) | `hash(32) ‖ height(8 BE) ‖ канонический блок` |
| `blocks_by_hash` | хеш блока (32 Б) | каноническое кодирование блока |
| `domains` | `DomainId` (32 Б, порядок байт) | `DomainStateBytes` (ниже) |
| `tlds` | `TldId` (32 Б, порядок байт) | `TldStateBytes` (ниже, M7d) |
| `dht_cache` | `DomainId` (32 Б) | байты `SignedDnsRecord` (непрозрачные) |
| `names_v3` (P0.2) | ключ индекса (32 Б, порядок байт) | целевой id (32 Б) |
| `name_reverse_v3` (P0.2) | целевой id (32 Б, порядок байт) | `tag(1) ‖ каноническое имя` |
| `meta` | `&[u8]` | `&[u8]` |
| `snapshot_v1_meta` (M6b) | `u64` = 0 (единственный слот) | `height(8 BE) ‖ tip_hash(32)` = ровно 40 Б |
| `snapshot_v1_domains` (M6b) | `DomainId` (32 Б, порядок байт) | `DomainStateBytes` (тот же формат, что `domains`) |
| `snapshot_v1_tlds` (M6b) | `TldId` (32 Б, порядок байт) | `TldStateBytes` (тот же формат, что `tlds`) |
| `tld_floors_v1` (опция владельца) | `TldId` (32 Б, порядок байт) | `u64` (порог истечения, неявный BE redb) |
| `snapshot_v1_floors` (M6b) | `TldId` (32 Б, порядок байт) | `u64` — замороженная копия порогов (состояние НА снапшоте, не тип) |

Дополнительный ключ `meta` (P0.3/P0.4):

| Ключ | Значение |
|---|---|
| `verified_snapshot_v1` (P0.3) | `height(8 BE) ‖ tip_hash(32) ‖ manifest_hash(32)` = 72 Б — маркер ПРОВЕРЕННОГО импортированного снапшота (зарезервирован, как `tip`) |

Ключи `meta`:

| Ключ | Значение |
|---|---|
| `format_version` | `u64 BE` = `STORAGE_FORMAT_VERSION` (1) |
| `tip` | хеш (32 Б) блока типa |
| `tip_height` | `u64 BE` (делает `tip()` O(1)) |
| `domain_count` | `u64 BE` (поддерживаемый счётчик) |
| `tld_count` | `u64 BE` (поддерживаемый счётчик, M7d) |

Заголовок `hash ‖ height` в `blocks_by_height` делает каждый
индекс самодостаточным (проверяемым без чтения блока); оба
индекса обновляются в одной транзакции.

### Конвенция генезиса

Генезисный блок детерминирован (константы протокола) и
**никогда не хранится** как байты. Свежее хранилище имеет
`tip == (0, genesis_hash)`; первый добавленный блок имеет высоту
1. Хеш генезиса всегда перевыводится
(`scone_blockchain::genesis_hash()`), никогда не читается.

## Формат кодирования `DomainStateBytes` (M8b)

57 или 89 байт в зависимости от ведущего тега версии,
целые фиксированной ширины big-endian (канонично, побайтно
сравнимо):

```text
DomainStateBytes = tag ‖ owner(32) ‖ sequence(8 BE) ‖ registered_at(8 BE)
                   ‖ valid_until(8 BE) [‖ record_hash(32)]

tag = 0x01 : record_hash present → exactly 89 bytes
tag = 0x02 : record_hash absent  → exactly 57 bytes
```

- `registered_at` / `valid_until` (M8b): срок регистрации
  (1 год при заявке, продлеваемый, см.
  `/docs/en/technical/blockchain.md`).

Кодировки M7 (41/73 байта, без срока) **нелегитимны** с M8b:
строгое декодирование → `Corrupted`. (Хранилище M7
регенерируется повтором: `load_chain_replay`.)

- `owner`: `OwnerId` (32 Б);
- `sequence`: последовательность последнего применённого
  `UpdateDomain` (0 сразу после `RegisterDomain`);
- `record_hash`: текущее обязательательство в цепочке набора
  DNS-записей (`None`, пока не применён ни один `UpdateDomain`).

**Строгое** декодирование (`DomainStateBytes::decode`):
неизвестный тег, неверная длина или лишние байты →
`StorageError::Corrupted`, никогда паника.

## Формат кодирования `TldStateBytes` (опция владельца)

Переменная длина в зависимости от варианта enum — 34 байта для
**частного** TLD, 2 для **открытого** (ни последовательности, ни
хеша записей):

```text
TldStateBytes = tag(0x04) ‖ flag(0x00|0x01) ‖ owner(32)? ‖ until(8)
```

- `flag` (опция владельца, enum `TldState`): `0x00` =
  `TldState::Open` (ничей — самообслуживание + PoW, без байт
  владельца), `0x01` = `TldState::Private` (следуют 32 байта
  владельца). Строго канонично — любой другой байт →
  `Corrupted`. Инвариант «открытый ⟺ без владельца»
  СТРУКТУРЕН: два состояния нельзя перепутать.
- **`until` (8 байт, BE64)**: собственные часы TLD — конец
  частного срока (заявка/продление + 3 года) или расписание
  смерти открытого (годовой порог при рождении, отодвигаемый
  каждым живым доменом). Это снова атрибут записи (изменение
  жизненного цикла TLD). Производная таблица `tld_floors_v1`
  (+ её замороженная копия `snapshot_v1_floors`) всё ещё
  отслеживает пороги, перестраиваясь при повторе и восстанав-
  ливаясь при загрузке — перезапущенный узел убивает те же TLD,
  что и непрерывный.

Кодировки M7d (33 байта, тег `0x01`), M8b (34 байта, тег `0x02`,
булево `open`) и наследуемый тег `0x03` (встроенный `until`)
**нелегитимны**: строгое декодирование → `Corrupted`
(перед-mainnet, регенерация через повтор — путь миграции).

Тег существует только для эволюции формата: будущий макет
поднимает тег, а старые читатели проваливаются с `Corrupted`
вместо гадания. **Строгое** декодирование
(`TldStateBytes::decode`): неизвестный тег, неверная длина,
лишние байты или неканонический флаг →
`StorageError::Corrupted`, никогда паника.

## Гарантии атомарности

`append_block_with_state` пишет в **одной** `WriteTransaction`
redb:

1. блок в `blocks_by_height` (предварительная проверка: высота
   не должна существовать с иным содержимым, иначе
   `StorageError::Conflict`);
2. блок в `blocks_by_hash`;
3. каждую дельту состояния домена (`domains`);
4. счётчик `domain_count` (увеличивается только на число
   **новых** доменов; `UpdateDomain` существующего домена его
   не увеличивает);
5. каждую дельту реестра TLD (`tlds`, M8b: заявки, передачи,
   открытие/закрытие) — **в той же транзакции**: блок,
   записанный без своих изменений TLD, структурно невозможен;
6. счётчик `tld_count` (только новые TLD);
7. каждое **удаление** (M8b): домены, истёкшие по
   детерминированному GC (`removed_domains`), и отозванные TLD
   (`removed_tlds`) покидают хранилище в той же транзакции,
   счётчики уменьшены — перезапуск никогда не воскресит
   истёкшую регистрацию;
8. дельты **индекса имён** P0.2 (upsert'ы и удаления, см. ниже)
   — те же гарантии: крах никогда не оставляет запись индекса,
   указывающую на отсутствующий домен;
9. `tip` и `tip_height`.

redb коммитит в стиле WAL: крах посреди записи оставляет
**предыдущее** когерентное состояние. **Блок, записанный без
своего состояния, следовательно, структурно невозможен** — это
ключевой инвариант вехи.

Дополнительные гарантии:

- **Монотонность**: добавление на высоте ≠ `tip_height + 1` →
  `StorageError::NonMonotonicHeight`, ничего не записано
  (проверяется *до* открытия транзакции записи);
- **Идемпотентность**: повторное добавление текущего блока типa
  с той же парой `(height, hash)` — пустая операция (быстрый
  путь сравнивает высоту и хеш; при равной высоте идентичные
  байты блока тоже молчаливая пустая операция, иные байты —
  `Conflict`);
- **Повреждённая база**: усечённый/загрязнённый файл →
  типизированная ошибка (`StorageError::Database`/`Corrupted`)
  при открытии или чтении, никогда паника (протестировано);
- **Версия формата**: `format_version` ≠ 1 →
  `StorageError::UnsupportedFormat` (требуется явный путь
  миграции, никогда гадание).

## Интеграция с блокчейном (`integration.rs`)

Разделение ролей: [`ChainState`] в ОЗУ = авторитет консенсуса;
хранилище = персистентность. Выбранная стратегия (простейшая,
как задокументировано): **персистировать состояние на каждом
блоке** — `store_block` пишет блок + состояния доменов,
**тронутых этим блоком** (дельта). Полный повтор остаётся
возможным и служит путём контроля/ремонта.

- `store_block(store, chain, block, hash)`: канонически кодирует
  блок, читает конечное состояние тронутых доменов И заявленных
  TLD из ОЗУ-состояния (уже обновлённого `push_block`),
  атомарное добавление.
- `load_chain(store)`: **без повтора** — читает тип + блок типa
  (чтения блоков O(1)), восстанавливает состояние доменов
  страницами по 100 (`DOMAIN_PAGE`) **и реестр TLD страницами
  по 100** (`TLD_PAGE`, M7d — закрытие окна перезапуска: без
  него перезапущенный узел забывал каждый заявленный TLD
  и отклонял каждый `RegisterDomain` под этим TLD с
  `UnknownTld`, хотя его диск держал полное состояние). ОЗУ-
  цепочка держит только генезис + тип; исторические блоки
  остаются в хранилище и отдаются из него. С M8 `load_chain`
  затем перестраивает **индекс анти-replay TXID** (см. ниже).
- `load_chain_replay(store)`: повторяет все сохранённые блоки
  один за другим (никогда все в ОЗУ) с полной валидацией;
  результирующий тип должен равняться сохранённому типу, иначе
  `Corrupted`.
- `rebuild_replay_index_from_store(store, chain, tip_height)`
  (M8): ресканирует последние
  `min(REPLAY_WINDOW_BLOCKS, tip_height)` персистентных блоков
  (один блок в ОЗУ за раз) и перевставляет каждый TxId в индекс
  цепочки **на его исходной высоте включения**, через публичный
  API `Blockchain::rebuild_replay_index` (без доступа
  к приватным полям). Отсутствующий блок под типом или
  недекодируемый в окне → `Corrupted` (эти байты уже послужили
  построению цепочки: сбой здесь сигнализирует повреждённое
  хранилище).
- `touched_domains(block)`: id доменов, изменённых транзакциями
  блока, дедуплицированы, порядок блока.
- `touched_tlds(block)`: id TLD, мутированных блоком
  (`RegisterTld`, `TransferTld`, `RevokeTld`, `SetTldOpen`),
  дедуплицированы, порядок блока (M8b).
- `store_block_with_removals(...)`: вариант `store_block`,
  также получающий домены, удалённые GC блока (M8b), для
  атомарной записи, описанной выше. Реле питает этот список из
  `Blockchain::push_block_with_gc` (результат применения
  выставляет `gc_removed_domains`). **GC-вытеснение кэша DHT**:
  записи `dht_cache` удалённых доменов удаляются в ТОЙ ЖЕ
  транзакции, что блок (дельты добавления несут таблицу
  `dht_cache`) — запись DHT никогда не переживает домен, которому
  служила, истёкшие записи никогда не копятся вечно (тест:
  `gc_evicts_the_dht_cache_entry`).

Реле (M4) будет использовать: `load_chain` при старте, затем
для каждого принятого блока `push_block` (ОЗУ), затем
`store_block` (диск).

## Персистирование реорга (`rewind_to_height` + `persist_state_snapshot`)

Реорг (переключение на более сильную ветвь-сестру) не может
пройти через монотонное добавление — запись победившего суффикса
провалилась бы с `NonMonotonicHeight`. Выделенный путь (фикс
залипающего меньшинства, реле + хранилище):

1. `rewind_to_height(fork_height)` — ОДНА транзакция redb
   удаляет блоки выше точки форка и возвращает `tip`/
   `tip_height` (индекс имён и живые состояния исправляются
   на следующем шаге);
2. `persist_state_snapshot(store, chain)` — перезаписывает
   живые таблицы (`domains`, `tlds`, индекс имён, пороги TLD)
   из экспорта пост-реоргового ОЗУ-состояния: живые таблицы
   НИКОГДА не описывают ПРОИГРАВШУЮ ветвь при загрузке;
3. монотонное повторное добавление усыновлённого суффикса
   (обычные дельты).

Сбой персистирования на этом пути логируется и деградирует
(хранилище заживляет при загрузке через повтор) — никогда не
фатален.

## Снапшот состояния загрузки (M6b)

`load_chain`, как описано выше, всё ещё O(размер состояния):
ни один блок не повторяется, но вся таблица `domains`
перечитывается. Именно путь «состояние-персистируется-на-блок»
делает повтор ненужным. Снапшот M6b адресует другую стоимость:
случай, когда ОЗУ-состояние нужно реконструировать **повтором**
(ремонт, контроль или бэкенд без персистирования состояния
на блок). Он предлагает загрузку в **O(tip − H)** — повторяя
только суффикс над снапшотом.

### Запись

- **Интервал**: `SNAPSHOT_INTERVAL = 64` (публичная константа
  `scone-storage`). Триггер — добавление блока
  `k·SNAPSHOT_INTERVAL + 1`: эта транзакция замораживает
  состояние живых таблиц **как оно есть до применения этого
  блока**, т. е. каноническое состояние после блока
  `k·SNAPSHOT_INTERVAL`.
- **Никогда на типе**: снапшот, следовательно, стоит на
  `tip − 1` в лучшем случае, всегда строго ниже типa в момент
  записи. Крах сразу после никогда не может оставить снапшот
  «выше» персистированной цепочки.
- **Атомарно**: заморозка (очистка + копия таблиц `domains`/
  `tlds` в `snapshot_v1_*`, запись `snapshot_v1_meta`) происходит
  в ТОЙ ЖЕ транзакции redb, что добавление триггерного блока —
  крах оставляет либо старый снапшот целым, либо новый полный
  со своим блоком (redb WAL).
- **Единый слот**: каждый снапшот ЗАМЕНЯЕТ предыдущий (таблицы
  опустошаются, затем копируются заново) — никакого накопления,
  никакого прунинга, след на диске ограничен ~2× состояния.
- Формат замороженных состояний — строго
  `DomainStateBytes`/`TldStateBytes` (повторное использование,
  без нового кодирования); только строка `snapshot_v1_meta` —
  новый формат (`height(8 BE) ‖ tip_hash(32)`, строгое
  декодирование: любая другая длина → `Corrupted`).

### Чтение при загрузке (`load_chain`)

1. Тип валидируется как всегда (хеш перевычислен из заголовка
   блока типa против `meta["tip"]`).
2. Если `snapshot_meta()` существует, его высота `H`
   удовлетворяет `0 < H < tip_height`, и ПЕРЕВЫЧИСЛЕННЫЙ хеш
   блока, сохранённого на `H`, равен `tip_hash` снапшота
   (**якорь** — снапшот, чужой персистированной цепочке,
   изменённый или из другого файла, обнаруживается здесь),
   замороженное состояние восстанавливается страницами по 100,
   затем повторяются только блоки `H+1..=tip` (полная валидация,
   идентичная живым блокам).
3. Тип, достигнутый повтором, должен равняться сохранённому.
4. **Любой сбой на этом пути (отсутствующий снапшот,
   непригодная высота, невалидный якорь, недекодируемые байты,
   проваленный повтор) молча деградирует к полной загрузке
   до-M6b** (чтение живых таблиц, без повтора) — плохой снапшот
   никогда не проваливает загрузку. Обратная совместимость —
   частный случай «нет снапшота»: хранилище, записанное до M6b
   (без таблиц `snapshot_v1_*`), грузится идентично,
   `snapshot_meta()` будучи `None`.

Повторяемый суффикс ограничен `SNAPSHOT_INTERVAL` (максимум 64
блока на момент триггера + намайненные с тех пор): загрузка
O(tip − H) с H гарантированно свежим.

## Индекс анти-replay TXID, перестраиваемый при загрузке (M8)

Индекс анти-replay (`included`, TxId → высота включения, окно
`REPLAY_WINDOW_BLOCKS = 256` — см.
`/docs/en/technical/blockchain.md`) — **чистая функция
канонической цепочки**: он никогда не персистируется. Поскольку
`load_chain` не повторяет историю, восстановленная цепочка
стартовала до M8 с **пустым** индексом — перезапущенный узел
принимал повторное включение любой транзакции, ещё в пределах
своего окна replay (задокументированное ограничение; правила
состояния оставались единственной защитой).

M8 закрывает это окно: после восстановления (полный путь ИЛИ
снапшот + повтор суффикса) `load_chain` вызывает
`rebuild_replay_index_from_store`, который перечитывает
последние `min(REPLAY_WINDOW_BLOCKS, tip_height)` персистентных
блоков — один блок в ОЗУ за раз, ограничение памяти как везде —
и перевставляет каждый TxId на его **исходной высоте**.
Хранилище с менее чем 256 блоками, следовательно, перестраивает
весь индекс.

Свойства:

- **Решения идентичны живому узлу**: те же записи, то же правило
  прунинга (`h > tip − 256`) — узел, который перезапускается,
  и узел, который никогда не останавливался, отклоняют те же
  replays (протестировано: точный счёт индекса и равенство
  с пруненным живым индексом).
- **Семантика прунинга не меняется**: транзакция старше окна
  остаётся допущенной индексом (и затем проваливается на
  правилах состояния, если применимо) — ровно как раньше.
- **Снапшот НЕ замораживает индекс**: повтор суффикса снапшота
  реконструирует записи выше H, рескан M8 добавляет часть окна
  НИЖЕ H (тот же контракт, что owner_keys/grace: перестраивается,
  никогда не персистируется).
- **Стоимость**: ≤ 256 точечных чтений блоков при загрузке,
  O(окно) — независимо от возраста цепочки.
- Отсутствующий или недекодируемый блок **внутри окна**
  проваливает загрузку с `Corrupted` (эти байты уже послужили
  построению цепочки); вне окна исторические блоки не тронуты.

`load_chain_replay` (нуль доверия) перестраивает индекс тем же
способом через свой полный повтор — оба пути сходятся.

## Персистентный индекс Имя → Id (P0.2)

`DomainId = BLAKE3-256(DOMAIN_ID_VERSION ‖ каноническое имя)`
необратим: разрешение имени (реле/DNS) требует персистентного
индекса. P0.2 добавляет его в хранилище с той же транзакционной
дисциплиной, что и остальное.

### Схема

Две таблицы-спутницы, записываемые и стираемые вместе:

```text
names_v3        key  = BLAKE3-256("SCONE-NAME-IDX-V1" ‖ canonical name)  (32 B)
                val  = target id (32 B : DomainId or TldId)

name_reverse_v3 key  = target id (32 B)
                val  = tag(0x01 domain | 0x02 TLD) ‖ canonical name
```

- Ключ `names_v3` — **хеш имени, а не открытое имя** (компактные
  индексные таблицы, никакого gossip имён через дампы). Ключ —
  **чистая функция имени**: индекс перестраиваем в любой момент
  из цепочки (`rebuild_name_index`), никакие дополнительные
  метаданные для него не персистируются.
- `name_reverse_v3` хранит имя (ровно один раз), потому что
  пути удаления (GC истёкших доменов, `RevokeTld`) знают только
  **id**: хешированный ключ для стирания как-то надо найти. Тег
  различает два пространства имён.
- Строгое разделение: `resolve_name` НИКОГДА не отвечает запись
  TLD, а `resolve_tld` — запись домена (решает тег обратной
  таблицы; у `DomainName` ≥ 2 метки, у TLD 1 — оба выведения
  ключей разделяют пространство `names_v3`, но не результаты).
- `DomainId` остаётся 32 байтами, никогда не урезается (жёсткое
  правило проекта: идентичность консенсуса, сопротивление
  коллизиям).

### Транзакционная согласованность

Upsert'ы (`RegisterDomain`, `AssignDomain`, `RegisterTld` — имена
несутся открытым текстом транзакциями) и удаления (GC, отзывы —
голые id) переносятся `StateDelta` блока (`name_upserts` /
`name_removals`) и применяются в **той же транзакции redb**, что
записи блока и состояния. Крах, следовательно, не может оставить
ни запись индекса, указывающую на отсутствующий домен (никаких
призраков), ни зарегистрированный домен без его записи.
Проваленное добавление ничего не пишет (протестировано).
Именованные варианты `put_domain_state_with_name` /
`put_tld_state_with_name` / `remove_domain_state` предлагают ту
же атомарность инструментам ремонта.

`store_block` / `store_block_with_removals` выводят дельты имён
из ТЕХ ЖЕ транзакций блока — без лишнего параметра на интерфейсе
реле.

### Перестройка (`RedbStore::rebuild_name_index`)

Индекс — чистая функция канонической цепочки, как и индекс
анти-replay M8. `rebuild_name_index` перестраивает его из
**персистированных блоков** (`DomainStateBytes` НЕ содержат
имени — только владелец/последовательность/истечение — так что
источник истины — поток транзакций, где `RegisterDomain`
и `AssignDomain` несут каноническое имя открытым текстом):

1. проход 1: скан `blocks_by_height` генезис→тип, один блок
   в ОЗУ за раз; собрать привязки `имя → id`, увиденные в
   `RegisterDomain`/`AssignDomain`/`RegisterTld`;
2. проход 2: фильтр только по **живым** целям (персистированное
   состояние авторитетно) — домен, зарегистрированный затем
   GC/истёкший, не переиндексируется;
3. проход 3: стереть + полная перезапись обеих таблиц в ОДНОЙ
   транзакции (крах → старый или новый полный индекс).

Отсутствующий или недекодируемый блок → `Corrupted` (те же
байты, что построили цепочку). Стоимость — O(различные имена)
в ОЗУ (≤ 253 Б на имя) и O(блоки) в чтениях — инструмент
ремонта, не путь загрузки.

### Чем индекс НЕ является

- Не авторитет: ОЗУ-состояние цепочки остаётся единственным
  авторитетом; индекс — перестраиваемый кэш (расхождение — баг
  транзакционности, обнаруживаемый `rebuild_name_index`,
  сравнённым с ним).
- Не заморожен в снапшоте M6b: таблицы `names_v3`/
  `name_reverse_v3` живые и следуют дельтам каждого блока;
  снапшот состояния их не встраивает (реконструкция дельтами
  при возобновлении или `rebuild_name_index` как ремонт).

### Чего снапшот НЕ закрепляет

ОЗУ-состояние `ChainState` несёт внутренние структуры, не
закрепляемые консенсусом (ключи владельцев, льготные окна). Они
НЕ замораживаются: повтор суффикса реконструирует их применением
транзакций (детерминированно, то же содержимое, что полный
повтор для соответствующего окна). Индекс анти-replay TXID
следует тому же контракту (M8, см. предыдущий раздел):
перестраивается при загрузке, никогда не замораживается.
Побитово-точное равенство с `load_chain_replay` проверено
тестом на каноническом состоянии (state_root + SMT).

## ПРОВЕРЕННЫЙ снапшот состояния — чанки + манифест + криптопроверка (P0.3)

Снапшот M6b выше ускоряет загрузку узла, доверяющего своему
диску. P0.3 адресует другую потребность: транспортировку
состояния между узлами (бутстрап нового узла, ремонт) без
доверия транспорту. Формат и проверка живут в
`crates/scone-storage/src/verified_snapshot.rs` + реконструкция
корня в
`crates/scone-blockchain/src/snapshot_verify.rs`.

### Модель доверия

Снапшот несёт состояние **финализированного** блока — чекпоинт,
подписанный кворумом комитета (`CheckpointData.state_root`,
корень O(1) `state_root_smt`). Подлинность чекпоинта (кворум
подписей Ed25519) валидируется слоем цепочки ДО импорта. Сам
импорт проверяет соответствие снапшот ↔ чекпоинт
ПЕРЕВЫЧИСЛЕНИЕМ:

1. **хеш каждой страницы**: `blake3("SCONE-SNAP-PAGE-HASH" ‖
   полное кодирование страницы)` должен равняться хешу,
   анонсированному манифестом (один фальсифицированный байт →
   отказ);
2. **сумма записей == счётчики манифеста** (отсутствующая
   страница или неверный счётчик → отказ);
3. **корень SMT, перевычисленный из импортированных записей ==
   `checkpoint.data.state_root`** — ТА криптографическая
   проверка: всё состояние (домены + TLD) рефолдится в свежий
   SMT (`snapshot_verify::recompute_state_root`, листья
   `SCONE-LEAF-DOM-V1`/`SCONE-LEAF-TLD-V1` ровно как живой
   путь), и корень должен равняться подписанному комитетом.
   Фальсифицированный, усечённый или неполный снапшот
   отклоняется ДО ЛЮБОЙ ЗАПИСИ;
4. **структурные согласованности**: `height`/`tip_hash`/
   `state_root` манифеста == таковые чекпоинта; строго
   возрастающие id (без дубликатов); последовательные индексы
   страниц; границы DoS (≤ 10 000 записей/страница,
   ≤ 2^20 страниц, общий бюджет).

Провал проверки → `StorageError::SnapshotRejected`, хранилище
остаётся строго неизменным (всё проверяется до транзакции
записи).

### Сериализованный формат (строгий, big-endian, безжалостное декодирование)

```text
manifest = "SCONE-SNAP-MAN-V1"
        ‖ height(8) ‖ tip_hash(32) ‖ state_root(32)
        ‖ page_count(4) ‖ domain_count(8) ‖ tld_count(8)
        ‖ page_hashes(page_count × 32)

page    = "SCONE-SNAP-PAGE-V1"
        ‖ index(4) ‖ height(8) ‖ state_root(32)      ← every page is
        ‖ entry_count(4) ‖ entries                   self-identifying

entry   = kind(0x01 domain | 0x02 TLD | 0x03 TLD floor) ‖ id(32)
          ‖ [len(2) ‖ state | floor(8 BE)]
          (state = DomainStateBytes 57/89 B or TldStateBytes 2/34 B —
           the existing canonical storage formats, reused; kind
           0x03 (lifetime floor of an open TLD, owner-option) has
           a dedicated format WITHOUT a length prefix:
           id(32) ‖ floor(8 BE), fixed size)
```

Порядок страниц: все записи доменов (возрастающие id), затем все
записи TLD (возрастающие id), затем пороги жизни TLD, ЗАМОРО-
ЖЕННЫЕ на высоте снапшота (`snapshot_tld_floors_all` — не живая
таблица) — порядок пагинации курсора хранилища. Каждая страница
несёт `(index, height, state_root чекпоинта, entries)`: одинокая
страница знает, какому снапшоту она принадлежит. Страницы по 256
записей при экспорте (`VERIFIED_SNAPSHOT_PAGE_ENTRIES`); границы
DoS при импорте. Пороги TLD (`tld_floors_v1`) — часть
переносимого формата: вид 0x03 несёт их, и импорт требует их
строго возрастающими и нацеленными на TLD, ПРИСУТСТВУЮЩИЙ
в снапшоте — иначе импортёр никогда не убил бы то, что убил бы
экспортёр (молчаливый форк, отказ).

### Экспорт (`export_verified_snapshot(store, checkpoint)`)

Сериализует состояние ПОСЛЕДНЕГО ФИНАЛИЗИРОВАННОГО ЧЕКПОИНТА —
не типa. Эмитирует домены, TLD, затем пороги жизни TLD,
замороженные на высоте снапшота (симметрия экспорт/импорт:
экспорт исторически опускал пороги — исправлено, регрессионный
тест `export_carries_tld_lifetime_floors`). Предпосылка:
хранилище держит персистированный снапшот M6b (`snapshot_v1_*`)
ровно на высоте чекпоинта (окно `CHECKPOINT_KEEP`/
`SNAPSHOT_INTERVAL` гарантирует, что такое состояние регулярно
доступно); якорь блока ПЕРЕВЫЧИСЛЯЕТСЯ из сохранённых байт
и должен равняться `checkpoint.data.block_hash`. Иначе →
`StorageError::SnapshotUnavailable` (экспорт — явное действие:
дождитесь следующего интервала/чекпоинта).

### Импорт (`import_verified_snapshot(store, checkpoint, manifest, pages)`)

Проверяет всё (см. выше), затем пишет в ОДНОЙ транзакции redb:
живые таблицы `domains`/`tlds` + счётчики + `tip = (H, хеш
чекпоинта)`, замороженные таблицы `snapshot_v1_*`, заякоренные
на том же блоке, и зарезервированный маркер
`meta["verified_snapshot_v1"]` (`height ‖ tip_hash ‖
manifest_hash`). Цель: только пустое хранилище (иначе
`SnapshotUnavailable`).

### Стоимость проверки (задокументировано)

Реконструкция SMT упорядоченными вставками: N записей × O(40)
хешей ≈ O(N·40). ~2.1 M хешей blake3 для 100 000 доменов
(десятки мс). ОДНОРАЗОВО — импорт бутстрапа/ремонта, никогда
путь на-блок: приемлемо. Упорядоченная вставка (возрастающие id)
создаёт каждую точку ветвления только один раз; в любом случае
корень зависит только от содержимого (гарантия SMT,
дифференциальный фаззинг в `smt.rs`).

## Бутстрап состояния — без повтора генезиса (P0.4)

Новый узел присоединяется к сети без повторения истории
с генезиса:

```text
finalized checkpoint (relay, validated by the chain layer)
        │
        ▼
verified snapshot (manifest + pages, crypto verification above)
        │  import → state at H + tip (H, hash) + marker
        ▼
anchor block H (requested from the network BY HASH — append_bootstrap_anchor)
        │
        ▼
recent blocks H+1..H+k (relay, increasing height, ordinary atomic
        │               append — the storage API requires only this)
        ▼
synced — boot replays ONLY the suffix above H
```

- **API хранилища для реле**: `append_bootstrap_anchor(H,
  hash, bytes)` (кладёт якорный блок: требуемый маркер,
  согласованность высоты/хеша с маркером, идемпотентно), затем
  обычное атомарное добавление по возрастающей высоте. Сетевое
  получение (по хешу из манифеста) — забота реле, не
  хранилища.
- **`load_chain`** распознаёт маркер: история ниже H
  законно отсутствует (неархивный узел). Конкретно: рескан окна
  анти-replay M8 имеет пол H (блоки ниже H не существуют и не
  отсутствуют); тип без сохранённого блока ПОСЛЕ импорта (якорь
  ещё не положен) → типизированная диагностика
  `SnapshotUnavailable` («якорь должен прийти из сети»), не
  порча.
- **Архивный против узла с полным состоянием**: архивный узел
  (флаг оператора) хранит всё — он отдаёт исторические блоки
  сети и грузится существующими путями. Узел с полным
  состоянием (умолчание P0.4 для нового узла, НАСТРОЕННОГО так)
  грузится на H: он валидирует будущие блоки (повтор суффикса),
  но не может отдавать историю ниже H или повторять генезис.
  **Поведение по умолчанию НЕ меняется**: этот путь активен,
  только если оператор явно запускает импорт
  (`import_verified_snapshot` — выделенное действие, никогда
  автоматическое); каждый существующий узел грузится
  идентично.
- **Равенство с полным узлом**: после присоединения суффикса
  H+1..H+k состояние, тип и `state_root_smt` побитово-точны
  с полным узлом на том же типе (протестировано); индекс
  анти-replay покрывает ровно tx на/выше H — неархивный узел
  не может знать окно ниже H, правила состояния остаются
  защитой (дублированная tx ниже H проваливается на состоянии,
  никогда не принимается дважды).

## Политика памяти

- **Курсоры везде**: `iterate_domains` ограничивает страницу
  `max` записями (100 по умолчанию) через ленивый `range`
  redb; вся таблица доменов никогда не материализуется. Большие
  списки (TLD, домены) обязательно через этот курсор
  (`iterate_tlds`, тот же контракт, M7d).
- **Только дельты**: `append_block_with_state` пишет только
  домены и TLD, изменённые блоком — никогда полное состояние;
- **Без синхронной дубликации**: ОЗУ-состояние не
  переперсистируется на блок; дисковое состояние не
  перезагружается на блок;
- **Точечные чтения**: каждое чтение открывает короткую
  транзакцию чтения, возвращает значение, закрывает;
  `AccessGuard`'ы redb живут только на время ограниченного
  копирования;
- **Исторические блоки никогда в ОЗУ**: `load_chain` грузит
  только тип; `load_chain_replay` стримит высоту за высотой;
- **Поддерживаемый счётчик**: `domain_count` — O(1), не скан.

## Границы DoS

Хранилище ограничивает то, что враждебный пир может заставить
его персистировать или аллоцировать:

- **`MAX_DHT_CACHE_ENTRY` (64 КиБ)**: большая запись DHT
  отклоняется до любой транзакции записи `put_dht_cache` →
  `StorageError::TooLarge` (ничего не записано);
- **`MAX_DOMAIN_PAGE` (10 000)**: `iterate_domains` *внутренне*
  ограничивает запрошенную страницу `min(max, 10_000)` —
  чрезмерный `max` никогда не материализует больше 10 000
  состояний в ОЗУ; у `iterate_tlds` та же граница
  (`MAX_TLD_PAGE`, M7d);
- **Зарезервированные ключи `meta`**: `meta_set` отклоняет
  `tip`, `tip_height`, `format_version`, `domain_count`,
  `tld_count` и `verified_snapshot_v1` (P0.3) с
  `StorageError::ReservedKey` — перезапись внутренней бухгалтерии
  хранилища молча испортила бы его.
- **Дважды ограниченный кэш DHT (LRU)**:
  `DHT_CACHE_MAX_ENTRIES` (100 000 записей) И
  `DHT_CACHE_MAX_BYTES` (2 ГиБ — защита враждебного случая;
  каждая запись уже ограничена 64 КиБ
  `MAX_DHT_CACHE_ENTRY`), какая граница раньше наступит, та
  вытесняет по порядку ключей. Счётчики (записи + байты)
  поддерживаются при записи — никогда скан для подсчёта;
  точная перестройка происходит только при открытии
  (единственный полный скан, при загрузке). Аксессоры
  `dht_cache_entries`/`dht_cache_bytes`, настраиваемые границы
  через `set_dht_cache_bounds` (тест:
  `dht_cache_respects_the_double_bound`).

## Модель доверия

Два пути загрузки, два уровня гарантии:

- **`load_chain` — доверие локальному диску**: хеш типa
  **перевычисляется** из заголовка блока типa и сравнивается
  с сохранённым `meta["tip"]` (расхождение →
  `StorageError::Corrupted`, никогда цепочка, восстановленная
  на поддельном хеше), состояния доменов строго декодируются.
  Однако исторические блоки **не повторяются**:
  персистированные состояния берутся на веру. Это быстрый старт
  узла, доверяющего собственному диску (записанному только этим
  же узлом, атомарно). С M6b этот путь сначала использует
  **снапшот состояния**, когда применим (см. ниже): якорь
  снапшота перевычисляется, и суффикс над H ревалидируется как
  живые блоки — повторяемая часть, следовательно, нуль-доверия,
  замороженная база — доверие диску.
- **`load_chain_replay` — нуль доверия**: все блоки
  перечитываются и ревалидируются один за другим (полная
  валидация, идентичная живым блокам); результирующий тип должен
  равняться сохранённому. Это инструмент контроля/ремонта.

**Рекомендация**: строгий узел (или узел, файл хранилища которого
мог быть подделан — общий диск, восстановление сомнительного
бэкапа) должен стартовать через `load_chain_replay`, а не
`load_chain`.

## Параллелизм

redb 4.x допускает **единственный объект `Database` на файл
и на процесс** (одновременное двойное `open` проваливается
с `DatabaseAlreadyOpen`). Поддерживаемая модель: клонированный
`RedbStore` (`Arc<Database>`), разделяемый между потоками —
писатели сериализованы `&mut self` + внутренней блокировкой
redb, одновременные читатели (снапшотные транзакции чтения).
После полного дропа всех дескрипторов файл можно открыть заново.

## Тесты (`tests/redb_store.rs` + модули `#[cfg(test)]`)

Каждый тест использует собственный tmpfile redb (`tempfile`).
Покрытие:

- круговорот блоков генезис→N, перезапуск, перечтение, повтор;
- M7d: реестр TLD персистируется атомарной дельтой,
  восстанавливается при перезапуске (`RegisterDomain` под TLD,
  заявленным до перезапуска, остаётся допустимым — окно
  закрыто), точные счётчики при повторном открытии,
  восходящий курсор `tlds`, проваленное добавление не оставляет
  TLD, зарезервированный ключ `tld_count` отклоняется;
- атомарность: проваленное добавление ничего не оставляет (тип,
  домены, индекс целы); дубликаты дельт считаются один раз;
- курсоры доменов: пагинация 100/7, восходящий порядок
  `DomainId`, старт строго после существующего или
  отсутствующего id, `max = 0`;
- точный счётчик `domain_count` (вставка/обновление/повторное
  открытие);
- круговорот кэша DHT + перезапись;
- параллелизм: чтения из двух потоков на клонированных
  дескрипторах;
- повреждённая база: усечённый / мусорный файл →
  типизированная ошибка, без паники (`catch_unwind`);
- M6b: снапшот записан на интервале, строго ниже типa; загрузка
  из снапшота = полный побитово-точный повтор (state_root +
  SMT, полное логическое состояние, тип); изменённый снапшот
  (испорченный tip_hash, недекодируемое состояние, высота >
  тип, meta неверной длины) → молчаливый откат к полной
  загрузке, та же конечная цепочка; повторённый суффикс <
  интервала; замена снапшота (без накопления) при пересечении
  интервала; хранилище до-M6b без таблиц снапшота грузится
  идентично;
- M8: индекс анти-replay перестроен при загрузке — tx,
  повторно включённая в окне, отклоняется (`TxReplay`) после
  восстановления; tx старше окна допускается (прунинг не
  меняется, решают правила состояния); точный счётчик == живой
  индекс (== `load_chain_replay`) для хранилища и короче, и
  длиннее окна; загрузка из снапшота: часть окна ниже H
  перестраивается ресканом, часть выше — повтором суффикса;
- P0.2: индекс имён — `resolve_name == DomainId::from_name`
  для 120 доменов (живой, после перезапуска, после стирания +
  перестройки), `resolve_tld` для заявленного TLD; GC истёкшего
  домена удаляет запись (без призраков), до и после
  перестройки; строгое разделение пространств домен/TLD;
  проваленное добавление не оставляет записи индекса; ключ
  индекса — задокументированное выведение BLAKE3;
- P0.3/P0.4 (`tests/verified_snapshot.rs`): экспорт → импорт →
  загрузка == полный повтор (состояние, тип, побитово-точный
  `state_root_smt`; импортированное состояние — состояние
  финализированного блока, не типa); страница, фальсифициро-
  ванная одним байтом → отказ до любой записи (хранилище строго
  неизменно); отсутствующая страница → отказ; неверный
  `state_root` (манифест ↔ чекпоинт, затем перевычисленный
  корень ≠ подписанный корень) → отказ; неверные счётчики /
  высоты / несогласованные типы / дубликаты id → отказ; импорт
  требует пустого хранилища; экспорт требует персистированный
  снапшот на высоте чекпоинта; контракт якоря
  (`append_bootstrap_anchor`: требуемый маркер, согласованность,
  идемпотентность); строгий сериализованный формат (лишние
  байты, теги, границы DoS); снапшот на H, затем блоки
  H+1..H+k присоединены → цепочка идентична полному узлу
  (состояние/тип/корень), загрузка без истории ниже H, индекс
  анти-replay = ровно tx на/выше H.
